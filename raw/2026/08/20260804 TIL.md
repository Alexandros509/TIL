
## 원본 필기 (Rough Notes)
(이곳에 사용자가 작성한 날것의 메모 원본을 그대로 붙여넣습니다.)
git add 전 해야할 단계
1. git status > git add -p > git diff --staged  
    git add -p (올리면서 검사하기) 
    - 전체 파일 내용 한 번에 올리지 않고, 코드를 조각조각 보면서 올릴지 말지(y/n) 디테일하게 스테이징(add)

    git diff --staged (최종 커밋 전 더블 체크)
    - 마지막으로 총점검

2. git commit 메세지 컨벤션   
 메세지 컨벤션 : 커밋 메세지 작성 시 팀원들 간 지키키로 약속한 일종의 규칙과 양식
    feat:__ : 기능 추가  
    fix:__ : 버그 수정  
    docs:__ : 문서화  
    refactor:__ : 리팩토리  
    chore:__ : 설정 변경  
    test:__ : 테스트 코드  

- 스테이징 + 커밋 수정 및 변경  
    1) 되돌리기 git reset
        1. --soft  : 커밋만 취소 ────> [ Staging 영역에 파일 남음 ] 
        2. --mixed : 커밋 + add 취소 ─> [ Working 디렉토리에 파일 남음 ] (디폴트)
        3. --hard  : 커밋 + add 취소 ─> [ 파일 변경내역까지 전부 삭제 ] (복구불가)
   
         `git reset HEAD~` : 방금 한 최신 커밋 1개를 취소하는 명령어.


    2) 블랙박스 git reflog
        - 작업 및 수정한 모든 발자취를 기록해둔 Reference log
        - git reset --hard로 삭제된 코드와 git log도 
          git reflog에는 reset을 했다는 행위 자체도 기록됨 
            · HEAD@{0} : 가장 최근에 한 행동

    reflog test 중 --hard로 삭제된 것은 --hard로 복구해야되며,
    Unstaged changes after reset:
    M       MEMBER.md
    D       PRODUCT.md
    수정(M), 삭제(D)라는 것을 확인.

    3) git revert
        커밋 기록 유지, 새로운 커밋 추가
        과거의 특정 커밋 내용을 취소하는 '정반대의 새로운 커밋'을 생성  
        기존 커밋 역사(History)를 지우지 않고 안전하게 변경 사항만 되돌리는 명령어

브랜치 (평행세계 / 시간선 분리)  
- 독립적 개발할 때 브랜치 사용  
   작은 범위로 하는게 관례
1. git branch "브랜치명"
    git branch order 물리적으로 분리되는 공간 추가 (커밋)
    후 git branch 로 확인. *가 현재 브랜치.

    빈 폴더에서는 branch가 안 됨

2. 브랜치 변경
    git checkout 브랜치명
        switch

    git switch -c 브랜치명 : 생성하며 이동

3. 브랜치명 컨벤션  
    feature/기능명 : 새 기능 개발 ex) feature/order-form  
    fix/버그명 : 오류 수정  
    bugfix/버그명 : 오류 수정  
    hotfix/긴급수정명 :  
    chore/설정명 : 로직과 무관한 설정/환경 변경  
    release/버전 : 최종 테스트, 버전 관리  
    test/테스트명 : 검증용 테스트  
    docs/문서명 :  문서 파일 추가 및 수정
    dev/ : feature 하나로 통합/테스트  

 4. 브랜치 병합
    1) merge commit 병합 커밋  
        3 way  
        두 브랜치 모두 새로운 작업이 있을 때, 양쪽 역사를 합친 '새로운 융합 커밋'을 생성하여 병합  
        git merge 병합브랜치명

    2) fast-forward 빨리 감기  
        기준 브랜치에 변경 사항이 없을 때, 별도 커밋 없이 기준 브랜치의 위치만 최신 작업 위치로 빨리 감아 이동시키는 병합
    3) conflict 충돌

5. 브랜치 삭제
    git branch -d 브랜치명

6. 브랜치명 변경
    git branch -m 변경할브랜치명
               -M              (강제변경) 같은 이름의 브랜치가 있어도 무시하고 강제로 덮어씀

 복잡하게 얽힌 커밋 히스토리를 일직선으로 깔끔하게 정리하는 명령어  
  - 충돌 > 해결 > 리베이스 진행 git rebase --continue  
        > 해결 X > rebase --skip 현재 충돌 건너뛰기  
                          --abort 전체 중단

"Merge하면 양쪽 다 변하나요?"

깨달음: 병합은 단방향 흡수다. git merge b를 치면 내가 있는 a 브랜치만 진화하고, b 브랜치는 과거 상태 그대로 멈춰있다.

"빈 폴더에서는 branch가 왜 안 만들어지나요?"

깨달음: 브랜치는 '커밋(발자국)'을 가리키는 이정표인데, 빈 폴더는 최초의 커밋(Initial Commit)조차 없어서 이정표가 가리킬 대상이 없기 때문.

"브랜치 이름 바꿀 때(-M) add, commit을 해야 하나요?"

깨달음: 브랜치 이름 변경은 파일 내용(코드)이 바뀐 게 아니라 캡슐의 '이름표'만 바꿔 낀 것이므로, commit을 할 필요 없이 바로 push 등 다음 작업을 하면 된다.

"Push 된 커밋은 왜 Rebase 하면 안 되나요?"

깨달음: Rebase는 커밋 식별자를 바꾸는 '역사 조작'이므로, 이미 깃허브에 공유되어 남들이 다운로드해 간 과거를 나 혼자 조작하면 팀원들의 Git 세계선이 전부 붕괴(충돌)하기 때문.
