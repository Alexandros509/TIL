# Docker · FastAPI MSA · EC2

### 왜 Docker인가

백엔드(FastAPI 등)를 서버에 올릴 때 Docker를 많이 쓴다.

개발 PC와 운영 서버의 OS·라이브러리 버전을 완전히 맞추기는 어렵다. 예전에는 가상머신(VM) 안에서 개발·테스트로 맞췄다. Docker는 그보다 가볍게 **원하는 실행 환경(아키텍처·OS·Python 버전·의존성)** 을 이미지로 고정한다.

- 최신 패키지보다 **개발과 같은 안전한 버전**을 고정
- `requirements.txt` → `pip install`을 Dockerfile에서 자동화
- 한 번 정의하면 로컬·EC2에서 같은 Compose로 기동

VM = 게스트 OS까지 올리는 무거운 가상화. 컨테이너 = 호스트 커널을 공유하고 프로세스·파일시스템만 격리. (필기: VM 대신 Docker로 환경을 맞춘다)

### Dockerfile로 환경 고정

필기에서 쓴 Dockerfile 골격(서비스별 `main.py`를 `ARG SERVICE`로 복사):

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt && useradd --uid 10001 --create-home app && mkdir /data && chown app:app /data
ARG SERVICE
COPY ${SERVICE}/main.py /app/main.py
USER app
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

포인트
- 베이스 이미지·의존성 레이어·**일반 사용자(`USER app`)** 실행
- 엔드포인트 진입은 `uvicorn main:app`
- 파일명은 `requirements.txt` (필기 오타 `requirement.txt` 아님)

### 서비스 분리(MSA)와 포트

하나의 `main.py`에 모든 기능이 몰리면 한 곳이 죽어도 전체가 무너지기 쉽다. 서비스를 나누면 장애 범위가 줄어든다.

다만 서비스마다 따로 기동·포트 맞추기는 번거롭다 → **Compose로 묶는다.**

포트
- 공개할 포트와 **숨길 포트**를 나눈다
- DB·내부 API를 호스트에 그대로 열면 SQL injection 등 공격면이 넓어진다
- 필기 예: “8001로 DB 접근 가능하면 위험”

같은 EC2(같은 Docker 네트워크) 안에서는 컨테이너끼리 통신이 된다. 밖(인터넷)으로 열 포트만 보안 그룹·`ports`로 제한한다.

### FastAPI · REST · Swagger

백엔드 설계 순서(필기)
1. API 정의서 — 엔드포인트 이름·메서드
2. REST: GET / POST / PUT / DELETE · CRUD
3. FastAPI로 구현 — **Swagger UI 기본 제공** (`/docs`)

예전엔 Python이 느리다는 인식이 있었으나, FastAPI 쪽으로 옮기는 사례가 늘었다는 수업 설명.

Git에 Dockerfile·Compose까지 올리면 배포 재현이 쉬워진다.

### EC2에 Compose 올리기

흐름(필기 + 수업 맥락)
1. EC2 생성 · AWS 보안 그룹으로 입구 제한
2. Ubuntu에 Docker(Compose 플러그인) 설치
3. 코드 전달(git clone 또는 압축 전송)
4. **`compose.yml` / `compose.yaml`이 있는 디렉터리**에서 실행

```bash
sudo docker compose up -d --build
sudo docker compose ps
```

주의
- 필기 `compose -up` → 실제는 `compose up` (`-` 없음)
- 바인딩이 `127.0.0.1`이면 외부(퍼블릭 IP)에서 안 들어온다 → 수업·교재에선 `0.0.0.0` / `BIND_HOST`로 맞춤
- 포트 번호 숨기기는 도메인·리버스 프록시 단계와 연결 (아래)

EC2·보안 그룹 기본기는 0915 노트와 이어진다.

## 핵심 개념

| 개념 | 한 줄 |
|---|---|
| Docker | 실행 환경(버전·의존성)을 이미지로 고정해 로컬=서버에 가깝게 |
| Dockerfile | 이미지 빌드 레시피 (`FROM` · `COPY` · `RUN` · `CMD`) |
| Compose | 여러 컨테이너(서비스)를 한 설정으로 up/ps/down |
| MSA(수업 범위) | 프로세스·배포 단위·데이터 소유권 분리. 한 EC2면 호스트 장애는 공유 |
| FastAPI / Swagger | REST API + `/docs`로 요청 시험 |
| 포트 공개 최소화 | 주문 API 등 필요한 것만 호스트·SG에 개방. DB·내부 서비스는 비공개 |
| BIND_HOST | EC2에서 `0.0.0.0`으로 바꿔 퍼블릭 접근 (로컬 기본은 loopback인 경우가 많음) |
| Route53 | 도메인·서브도메인 DNS (필기에서 후속으로 언급) |

## 교재 보충

출처: [튜터 블로그 — FastAPI MSA · Compose · EC2](https://velog.io/@roboticsmaster/FastAPI-MSA-Docker-Compose%EC%97%90%EC%84%9C-EC2%EA%B9%8C%EC%A7%80)

**서비스 예 (products / orders)**
- `products`: 읽기 전용 상품. **외부 포트 비공개**
- `orders`: 상품 API를 조회한 뒤 주문 저장(SQLite 볼륨). 호스트 **8000** 공개
- Compose 서비스 이름 `products`가 **DNS 이름**. 주문 컨테이너 안 `localhost`는 **주문 자신**이라 상품에 닿지 않음 → `http://products:8000` 형태

**MSA 경계**
- 실습은 분리 연습. MSA ≠ 곧바로 고가용성·무중단. EC2 한 대면 호스트 장애는 같이 맞음

**로컬**
```bash
docker compose up -d --build --wait
docker compose ps
# http://localhost:8000/docs
```
- `docker compose stop products` → 새 주문 503, 기존 주문 조회는 200 가능

**EC2**
- Ubuntu 24.04 기준 서술. SG: **22·8000을 본인 IP만**. products/DB 포트는 열지 않음
- `.env` 예: `BIND_HOST=0.0.0.0` / `API_PORT=8000` (로컬 기본이 `127.0.0.1`인 설정과 대비)
- `sudo docker compose up -d --build --wait`

**down vs down -v**
- `docker compose down` — 컨테이너 종료, **명명 볼륨 보존** (주문 데이터 유지)
- `docker compose down -v` — 볼륨까지 삭제 (복구 불가에 가깝게 실습 데이터 소거)

**localhost 함정 (퀴즈 요지)**
- 컨테이너 안에서 `localhost:8000`으로 다른 서비스를 치면 실패한다
- `ports`가 없어도 Compose 기본 네트워크 안에서는 **컨테이너 포트 + 서비스 DNS**로 통신 가능. `ports`는 호스트에 여는 설정

## 확인이 필요한 사항

- **`cpu lam` 필기** — “cpu lam 운영체제 가능”으로 보임. ARM/x86 등 **CPU·아키텍처** 언급 오타 가능성. 원문 의도 불명 → 확인
- **`compose -up` vs `compose up`** — 필기 `-up`은 오타로 보고 본문은 `compose up`으로 수정. 원문 표기는 확인용으로 남김
- **블로그 첨부** — 필기 “나중에 튜터님 블로그 링크 내용 첨부” → 이번 편집에서 참고·교재 보충에 반영. 원문 raw는 수정하지 않음
