## 어제의 복습

1. 사용자가 입력한 자연어 질문을 벡터 저장소에서 검색하기 위해 가장 먼저 수행해야 하는 작업으로 가장 알맞은 것
   - 질문 문장을 임베딩 모델에 입력하여 고차원 벡터 좌표로 변환한다
2. LangChain에서 벡터 유사도 계산 전에 연도, 카테고리, 대상자 등 문서에 부착된 속성 정보를 기준으로 검색 후보군을 사전에 좁히는 기법
   - 메타데이터 필터링
3. PGVector에서 코사인 거리(Cosine Distance) 지표를 사용할 때, 검색된 문서의 유사도 점수 해석으로 가장 알맞은 것
   - 점수가 0에 가까울수록 질문과 문서의 의미가 더 가깝다
4. RAG 파이프라인에서 Top-k 값을 100처럼 과도하게 크게 설정했을 때 발생할 수 있는 현상으로 가장 적절한 것
   - LLM에 전달되는 문맥에 노이즈가 많아지고 입력 토큰 비용이 증가한다
5. BM25와 같은 키워드 검색기와 PostgreSQL 벡터 검색기를 결합하여 단어 일치와 의미 유사도를 모두 반영하는 검색 방식
   - 하이브리드 검색

**4장 3강 : Re-ranking (1)**

Re-ranking 기법, 재순위 산출.

> 교재 · 4장 3강

**Re-ranking**은 1차로 빠르게 건져 낸 문서 후보를 정밀하게 다시 채점해 순서를 바꾸는 기법이다. 질문과 후보 문서가 얼마나 밀접한지를 정량 점수로 바꾸는 것이 1차 검색과 재순위의 공통 목적이다.

교안은 이 흐름을 **2단계 검색**(2-Stage Search)으로 설명한다.

- 1단계 (Retrieval, 빠른 추출): 방대한 DB에서 관련 가능성이 있는 상위 문서(Top-N, 보통 10~30개)를 키워드·벡터·하이브리드 검색으로 빠르게 수집한다
- 2단계 (Re-ranking, 정밀 재배열): 그 소수 문서만 질문과 1:1로 대조해 최종 상위 문서(Top-K, 보통 2~5개)를 맨 위로 재배치한다

### 1. Bi-Encoder (1차 검색 / Retriever)

- 처리 구조: **Bi-Encoder**는 질문과 문서를 각각 독립적으로 임베딩 벡터로 변환한 뒤, 두 벡터 간 코사인 유사도 등을 계산해 점수를 낸다
- 장점 1. 속도: 단순 벡터 내적·거리 계산만 하므로 초고속 검색이 가능하다
- 장점 2. 캐싱(사전 임베딩) 가능: 문서를 미리 벡터 DB에 저장해 둘 수 있어 수백만 건 탐색에 유리하다
- 단점: 맥락 파악 능력은 보통이다. 질문과 문서를 따로 압축한 뒤 비교하므로 세부 단어 사이의 미묘한 문맥 상호작용이 손실된다

### 2. Cross-Encoder (재순위화 / Re-ranker)

- 처리 구조: **Cross-Encoder**는 질문과 문서를 하나로 합쳐 트랜스포머 인코더 모델에 동시에 입력한 뒤, 이진 분류(0~1 사이 관련도 확률 점수) 형태로 최종 점수를 낸다
- 장점: 맥락 파악 능력이 높다. 모델 내부 Attention이 질문의 모든 토큰과 문서의 모든 토큰을 직접 대조해 정밀도를 극대화한다
- 단점: 연산량이 크고 느리다. 질문이 들어올 때마다 (질문 + 후보 문서) 쌍 개수만큼 트랜스포머 순전파를 매번 실행해야 하므로 전체 DB 대상 사용은 불가하다

### 3. 아키텍처 비교 요약

| 구분         | Bi-Encoder                                | Cross-Encoder                                   |
| ------------ | ----------------------------------------- | ----------------------------------------------- |
| 입력 및 연산 | 질문 → 임베딩 / 문서 → 임베딩 (개별 처리) | 질문 + 문서 동시 입력 → 트랜스포머 인코더       |
| 점수 산출    | 코사인 유사도 등 벡터 거리 기반 점수      | 0~1 사이 관련도 확률 점수 (이진 분류 기반)      |
| 속도 및 캐싱 | 매우 빠름, 문서 벡터 사전 캐싱 가능       | 연산량 크고 느림, 실시간 쌍(Pair) 추론 필수     |
| 맥락 이해도  | 보통 — 1차 후보 추출(Retrieval)용         | 매우 높음 — 소수 후보 정밀 재순위(Re-ranking)용 |

한 줄 요약: Bi-Encoder는 질문과 문서를 따로 벡터화해 캐싱과 속도를 극대화하는 1차 검색기이고, Cross-Encoder는 질문과 문서를 함께 트랜스포머에 넣어 연산은 느리지만 문맥 파악 능력을 극대화하는 2차 재순위화 모델이다.

```python
from langchain_community.cross_encoders import HuggingFaceCrossEncoder
from langchain_classic.retrievers.document_compressors import CrossEncoderReranker
from langchain_classic.retrievers import ContextualCompressionRetriever

cross_encoder_model = HuggingFaceCrossEncoder(model_name="Dongjin-kr/ko-reranker")

reranker = CrossEncoderReranker(
    model=cross_encoder_model,
    top_n=2
)

rerank_retriever = ContextualCompressionRetriever(
    base_compressor=reranker,
    base_retriever=bm25_retriever
)
```

```python
query = "사내 망 들어가려다 비밀번호 여러 번 틀렸을 때 처리 방법"

print("=== BM25 ===")
bm25_docs = bm25_retriever.invoke(query)
for i, doc in enumerate(bm25_docs, 1):
    print(f"Rank:{i}, Doc:{doc.page_content}")

print("=== ReRanker ===")
rerank_docs = rerank_retriever.invoke(query)
for i, doc in enumerate(rerank_docs, 1):
    print(f"Rank:{i}, Doc:{doc.page_content}")
```

**5장 5강 : 맥락 압축·검색 최적화 (1)**

> 교재 · 5장 5강

### 1. 맥락 압축 개념

**맥락 압축**(Contextual Compression)은 1차 검색된 문서 청크 전체를 LLM에 그대로 넘기지 않고, 질문과 직접 연관된 핵심 문장만 발췌하거나 무관한 문장을 제거해 전달하는 RAG 후처리 최적화 기법이다.

### 2. 기존 문서 전체 전달 방식의 3대 한계

- 토큰 낭비 및 비용 증가: 질문과 무관한 수천 자의 배경 텍스트가 프롬프트에 포함되어 API 비용 및 입력 처리 시간이 증가한다
- **Lost in the Middle** (중간 정보 누락): LLM이 긴 컨텍스트의 시작과 끝부분에 비해 중간에 위치한 핵심 근거를 놓치는 현상
- 환각(Hallucination) 유발: 같은 문서 내 다른 조건·수치·예외 규정이 노이즈로 작용해 모델의 답변 정확도를 떨어뜨린다

### 3. 맥락 압축의 2단계 동작 원리

1. 1단계 (기본 검색 / Base Retriever): BM25 또는 벡터 검색기를 통해 질문과 관련된 후보 문서를 우선 확보한다
2. 2단계 (문맥 압축 / Document Compressor): 확보된 문서를 압축기에 통과시켜 질문을 기준으로 불필요한 문장을 삭제하거나 핵심을 요약한다.
   구현 방식 예시는 다음이다.

- `LLMChainExtractor`
- `EmbeddingsFilter`
- `DocumentCompressorPipeline`

### 4. 기존 방식 vs 맥락 압축 비교

| 비교 항목   | 기존 문서 전체 전달 (Full Document)       | 맥락 압축 (Contextual Compression)          |
| ----------- | ----------------------------------------- | ------------------------------------------- |
| 전달 데이터 | 검색된 원본 문서 청크 전체 (수천 자)      | 질문에 맞게 정제된 핵심 문장 (수십~수백 자) |
| 토큰 소모량 | 큼 (최종 LLM 호출 비용·지연 증가)         | 적음 (최종 프롬프트 토큰 대폭 절감)         |
| 노이즈 비율 | 높음 (질문과 무관한 문맥 다수 포함)       | 최소화 (정답 근거 문장만 선별 유지)         |
| 답변 신뢰도 | 주변 잡음 정보로 인한 왜곡·환각 위험 존재 | 명확한 근거에 집중하여 정확도 향상          |

한 줄 요약: 맥락 압축은 1차 검색된 긴 문서에서 질문과 무관한 노이즈를 깎아내고 핵심 근거 문장만 남김으로써, 토큰 비용 절감과 Lost in the Middle 현상 방지를 동시에 달성하는 후처리 기법이다.

아래는 PC `chapter05/05_05.ipynb` 실습이다. 복지·휴가·근무 문서 3개를 BM25로 먼저 찾고, `LLMChainExtractor`로 질문과 관련된 문장만 남긴다. 이 노트북은 튜터 GitHub 12_rag에는 없다.

```python
# 문서 객체와 기본 키워드 검색기 모듈을 가져옵니다.
from langchain_core.documents import Document
from langchain_community.retrievers import BM25Retriever

# 여러 주제가 혼합된 실습용 사내 규정 문서를 정의합니다.
raw_documents = [
    Document(
        page_content="복지 제도 안내: 사내 복지 포인트는 매년 1월 1일에 100만 포인트가 지급됩니다. "
                     "포인트는 자기계발 및 문화생활에 사용 가능하며, 미사용 잔여 포인트는 당해 연도 12월 31일에 전액 소멸되어 다음 해로 이월되지 않습니다."
    ),
    Document(
        page_content="휴가 규정 안내: 연차 유급휴가는 1년간 80% 이상 출근 시 15일이 부여됩니다. "
                     "경조사 휴가는 사유 발생일로부터 사용해야 하며, 미사용 연차는 연말에 수당으로 정산 지급됩니다."
    ),
    Document(
        page_content="근무 환경 가이드: 사무실 내 회의실 예약은 사내 인트라넷 시스템을 통해 최소 1시간 전에 신청해야 합니다. "
                     "점심시간은 12시 30분부터 13시 30분까지이며 부서별 자율 운영이 가능합니다."
    )
]

# 공백 기준 단순 토크나이저 함수를 정의합니다.
def custom_tokenizer(text: str) -> list[str]:
    # 문장을 띄어쓰기 단위로 분리하여 단어 리스트를 반환합니다.
    return text.split()

# 1단계 기본 검색기(BM25)를 생성하고 검색 개수를 1개로 설정합니다.
base_retriever = BM25Retriever.from_documents(
    documents=raw_documents,
    preprocess_func=custom_tokenizer
)
base_retriever.k = 2
```

```python
from langchain.chat_models import init_chat_model

from langchain_classic.retrievers import ContextualCompressionRetriever

model = init_chat_model(
    model="gpt-6-luna",
)

compressor = LLMChainExtractor.from_llm(model)

compression_retriever = ContextualCompressionRetriever(
    base_compressor=compressor,
    base_retriever=base_retriever
)
```

**5장 6강 : 질의 유형별 검색 결과 비교 (1)**

> 교재 · 5장 6강

### 1. 질의 유형별 검색 인식 차이

- 사용자의 질문이 정확한 단어 일치를 요구하는지, 문맥적 뉘앙스를 요구하는지에 따라 검색 엔진의 성능 편차가 발생한다
- 단일 검색 방식만 고집할 경우 특정 유형의 질의에서 구조적인 검색 실패(Retrieval Failure)가 발생한다

### 2. 대표적인 3가지 질의 유형

- 고유명사·단순 키워드형 (Exact Keyword): 문서 내에 명시된 특정 에러 코드, 제품명, 약어, 규정 조항 번호 등 정확한 문자열 매칭이 필요한 질문
- 의미 탐색형 (Semantic / Intent): 원본 문서의 공식 용어와 단어는 다르지만, 일상적인 구어체나 동의어·유의어로 의도를 묻는 질문
- 복합 조건형 (Complex Multi-condition): 여러 제약 조건(시기, 대상, 예외 상황 등)이 얽혀 있어 문맥 해석과 조건 분리가 동시에 필요한 질문

### 3. 검색 전략별 비교 및 실패 메커니즘

| 비교 항목      | 키워드 검색 (BM25 / Sparse)                                     | 벡터 검색 (Vector / Dense)                                                            |
| -------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 작동 원리      | 텍스트 내 특정 단어의 출현 빈도(TF)와 희소성(IDF) 계산          | 문장을 다차원 임베딩 벡터로 변환 후 의미 거리(코사인 유사도 등) 계산                  |
| 강점 영역      | 고유명사, 코드, 약어, 법령·규정 조항 번호 검색                  | 동의어, 유의어, 의역된 구어체 기반 문맥 검색                                          |
| 주요 실패 원인 | 어휘 불일치 (Vocabulary Mismatch): 단어 표현만 달라도 검색 누락 | 의미 희석 및 뭉뚱그림: 신조어·전문 코드 왜곡, 조건은 다르지만 주제만 비슷한 문서 오탐 |

**Vocabulary Mismatch**는 키워드 검색의 대표 실패 원인이다. 벡터 검색은 반대로 전문 용어·세부 조건의 의미가 희석되어 실패할 수 있다.

한 줄 요약: 키워드 검색은 단어 불일치(Vocabulary Mismatch)로, 벡터 검색은 전문 용어·세부 조건의 의미 희석으로 실패하므로, 질의 유형에 맞춰 하이브리드 검색 및 질의 변환(Query Transformation)을 결합해야 한다.

**5장 7강 : 검색 전략 선택·개선 (1)**

> 교재 · 5장 7강

### 1. 검색 전략 선택 기준 정립

- 모든 질문을 단일 검색 파이프라인으로 처리하지 않고, 질문의 형태적 특징과 어휘 성격을 기준으로 가장 성공 확률이 높은 검색기를 매핑하는 규칙을 수립한다

### 2. 질의 유형별 최적 검색 전략 매핑

| 질의 유형              | 대표적 특징                                    | 최적 검색 전략                       | 선택 근거                                                                       |
| ---------------------- | ---------------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------- |
| 고유명사·단순 키워드형 | 시스템 코드, 약어, 제품명, 규정 조항 번호 포함 | 키워드 검색 (BM25)                   | 단어 형태의 100% 일치가 핵심이므로 임베딩 왜곡 없는 정확한 텍스트 매칭이 유리함 |
| 의미 탐색형            | 일상 구어체, 동의어, 유의어, 상황 묘사 중심    | 벡터 검색 (Vector)                   | 표면 단어가 달라도 문맥적 의도를 포착하는 다차원 임베딩 유사도가 유리함         |
| 복합 조건형            | 여러 제약 조건과 문맥이 얽힌 복합 질의         | 하이브리드 검색 (Hybrid) + 질의 분해 | 특정 조건 키워드 일치와 전체 문맥의 포괄적 해석이 동시에 요구됨                 |

### 3. 동적 라우팅 원리

**Query Routing**은 사용자의 질문을 검색 엔진에 곧바로 전달하지 않고, 분류기(Router)가 먼저 질문의 의도와 형태를 분석해 최적의 검색 경로로 분기시키는 기법이다.

핵심 역할:

- 고유명사·코드 포함 질의 → 키워드 검색기(BM25)로 라우팅
- 서술형·의미 중심 질의 → 벡터 검색기(Vector DB)로 라우팅
- 복합·다중 조건 질의 → 하이브리드 검색기 또는 다중 DB 병렬 검색으로 분기

구현 방식: 정규식/키워드 룰 기반 분기, 경량 분류 모델, 또는 LLM Structured Output(Function Calling)을 활용한 의도 분류

한 줄 요약: Query Routing은 질문의 형태적 특징을 먼저 판별해 키워드형은 BM25로, 의미 탐색형은 벡터 검색으로, 복합 조건형은 하이브리드 파이프라인으로 동적 분기시킴으로써 검색 누락과 불필요한 연산을 동시에 줄이는 전략이다.

**이해 잘못한 부분 / 피드백**

제시한 내용은 질의 성격에 따른 검색 전략 매핑과 동적 라우팅(Query Routing)의 핵심 역할을 정확하게 정리했다.
다만 실무에서 Query Routing을 설계할 때는 단일 검색기 분기(Logical Routing)뿐만 아니라 데이터 소스 및 파라미터 동적 선택(Semantic/Metadata Routing)까지 포함한다는 점이 중요하다. 또한 분류기(Router)로 매번 LLM을 호출하면 응답 지연(Latency)이 발생하므로, 단순 키워드 패턴(정규식/코드 패턴)은 룰 기반으로 먼저 거르고, 의도 분류가 필요한 경우에만 경량 LLM(Structured Output)이나 소형 분류 모델을 태우는 것이 실무 최적화의 핵심이다.

**4장 4강 : Query 변환 기법 (1)**

> 교재 · 4장 4강

### 1. Query 변환 개념

**Query 변환**(Query Transformation)은 사용자의 날것(Raw) 자연어 질문을 벡터 DB나 키워드 검색기가 가장 정확하게 매칭할 수 있는 최적화된 검색용 질의로 가공·재작성하는 Pre-Retrieval(검색 전단계) 기법이다.

### 2. 검색 전단계(Pre-Retrieval) 최적화의 3대 필요성

- 어휘 불일치(Vocabulary Mismatch) 해소: 사용자의 구어체·일상어 질문과 DB 내 공식·전문 문서 간의 단어 표현 격차 극복
- 모호성 및 생략 제거: 오타, 축약어, 지시대명사("그거", "방금 말한 것") 등을 문맥에 맞는 명확한 명사로 복원
- 검색 품질 사전 확보: 부실한 입력 질의로 인한 1차 검색 실패(Retrieval Failure)를 후처리(Re-ranking) 이전에 선제적으로 차단

### 3. 질의 특성별 4대 변환 기법 비교

| 기법             | 영문 표기                               | 핵심 동작                                                                                                         | 최적 적용 시나리오                                                  |
| ---------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 질문 재작성      | Query Rewrite                           | 맞춤법·오타 교정 및 불필요한 서술어를 제거하고 핵심 키워드 중심으로 재구성                                        | 질문이 지나치게 짧거나 은어·오타·구어체가 많이 포함된 경우          |
| 가설 문서 임베딩 | HyDE (Hypothetical Document Embeddings) | 질문에 대한 가상의 예상 답변 문서를 LLM으로 먼저 생성한 뒤, 그 가상 답변의 임베딩으로 유사 문서 검색              | 짧은 질문과 전문 문서(정답) 간의 문체·길이·의미 공간 격차가 큰 경우 |
| 질문 라우팅      | Query Routing                           | 질문의 의도와 도메인을 판별하여 가장 적합한 검색기나 데이터 저장소로 경로 분기                                    | 복수의 특화 DB(벡터 DB, RDB/SQL, 웹 검색, BM25 등)가 혼재된 환경    |
| 대화 맥락 반영   | Contextualize / Memory 기반 재구성      | 이전 대화 히스토리(Chat History)를 참조해 생략된 주어·목적어·대명사를 포함한 독립 질문(Standalone Query)으로 변환 | 멀티턴(Multi-turn) 챗봇 환경에서 꼬리 질문을 연속 처리하는 경우     |

**Query Rewrite**는 짧은 구어·오타를 핵심 명사 중심으로 다시 쓰는 기법이다.

**HyDE**(Hypothetical Document Embeddings)는 가상의 예상 답변을 먼저 만든 뒤 그 임베딩으로 검색한다.

실무 보완: 복잡한 다중 조건 질문의 경우 하나의 질문을 여러 개의 하위 질문으로 쪼개 병렬 검색하는 Query Decomposition / Multi-Query 기법도 함께 활용된다.

한 줄 요약: Query 변환은 1차 검색의 성패를 가르는 전처리 단계로, 단순 정제는 Query Rewrite, 문체·의미 격차 극복은 HyDE, 저장소 분기는 Query Routing, 멀티턴 대명사 복원은 대화 맥락 반영 전략을 선택해 검색 정확도를 선제적으로 끌어올린다.

**이해 잘못한 부분 / 피드백**

제시한 내용은 검색 전단계(Pre-Retrieval)에서 Query 변환이 필요한 이유와 4대 핵심 전략(Query Rewrite, HyDE, Query Routing, 대화 맥락 반영)을 매우 명확하고 체계적으로 정리했다.
다만 실무에서 Query Transformation을 적용할 때 가장 주의해야 할 점은 모든 변환 기법이 추가적인 LLM 호출(Latency 및 토큰 비용)을 유발한다는 것이다. 특히 HyDE(가설 문서 임베딩)는 LLM이 가상의 답변을 먼저 생성하므로 응답 시간이 크게 늘어나며, 도메인 지식이 전혀 없는 최신 고유명사나 코드에 대해서는 LLM이 지어낸 잘못된 가설 문서(환각)로 인해 오히려 엉뚱한 문서를 검색하는 역효과가 날 수 있다는 트레이드오프를 반드시 함께 고려해야 한다.

아래는 PC `chapter05/04_04.ipynb` 실습이다. Query Rewrite와 HyDE를 각각 한 번씩 호출한다. 이 파일은 튜터 GitHub 12_rag에는 없고, PC에서는 chapter05 폴더에 있다.

```python
from langchain.chat_models import init_chat_model
from langchain_core.prompts import PromptTemplate

model = init_chat_model(
    model = "gpt-6-luna",
    model_provider = "openai",
    reasoning_effort = "low"
)

rewrite_prompt = PromptTemplate.from_template(
    """
    사용자의 질문을 검색 시스템이 문서를 탐색하기 유리하도록 핵심 명사 중심의 명확한 문장으로 다시 작성하세요.

    사용자의 질문: {question}
    변환된 질문:
    """
)

rewrite_chain = rewrite_prompt | model

raw_query = "사과폰 최신형 배터리 얼마나 가?"
rewrite_query = rewrite_chain.invoke({"question": raw_query})

print(f"원본 질문: {raw_query}")
print(f"변환된 질문: {rewrite_query.content}")
```

```text
원본 질문: 사과폰 최신형 배터리 얼마나 가?
변환된 질문: 최신 아이폰 모델의 배터리 사용 시간은 얼마나 되나요?
```

```python
# HyDE

hyde_prompt = PromptTemplate.from_template(
    """
    다음 질문에 대한 객관적인 사실을 서술하는 한 단락의 학술적 답변을 작성하세요.

    질문: {question}
    가설 답변:
    """
)

hyde_chain = hyde_prompt | model

hyde_query = "열이 펄펄 끓고 목이 따가울 때 먹는 약"
hyde_doc = hyde_chain.invoke({"question": hyde_query})

print(f"원본 질문: {hyde_query}")
print("[HyDE 가설 문서]")
print(hyde_doc.content)
```

```text
원본 질문: 열이 펄펄 끓고 목이 따가울 때 먹는 약
[HyDE 가설 문서]
열과 인후통에는 증상 완화를 위해 성인은 아세트아미노펜 또는 이부프로펜을 제품 설명서에 따라 복용할 수 있으며, 간질환·과음이 있거나 다른 감기약에 아세트아미노펜이 포함된 경우에는 중복 복용에 주의해야 합니다. 이부프로펜은 위궤양, 신장질환, 특정 혈액응고 문제, 임신 중인 경우 등에 적합하지 않을 수 있으므로 약사나 의료진과 상의하는 것이 좋습니다. 충분한 수분 섭취와 휴식도 도움이 되며, 항생제는 세균 감염이 확인되거나 의료진이 필요하다고 판단한 경우에만 사용합니다. 호흡곤란이나 침도 삼키기 어려운 증상이 있거나, 고열이 지속·악화되거나 증상이 심해지면 진료를 받아야 합니다.
```

구어 «사과폰»이 «아이폰»으로 정제되었고, HyDE는 해열·인후통 약에 대한 가설 단락을 만들었다. 출력은 모두 `.content`로 문자열만 꺼낸 결과다.

### 출력물의 정체: LangChain AIMessage 객체

체인 끝이 모델이고 출력 파서가 없으면, 호출 결과는 문자열이 아니다.
이때 반환되는 것이 **AIMessage** 객체다. 출력 파서는 `StrOutputParser()`다.

### 구성 요소별 역할 분해

### 실무에서 깔끔하게 문자열만 뽑는 2가지 방법

1. 출력 시 `.content` 속성 접근 (현재 코드 방식):

2. 체인 끝에 `StrOutputParser()` 연결 (가장 보편적):
   - 체인 끝을 `rewrite_prompt | model | StrOutputParser()`로 구성한다.
     그러면 `invoke()` 결과 자체가 바로 문자열로 반환된다.
     속성 접근 없이 다음 검색기 입력으로 넘길 수 있다.

한 줄 요약: 저 긴 출력물은 출력 파서가 없는 체인에서 모델 호출이 반환한 AIMessage 객체 자체를 속성 접근 없이 출력했을 때 나타난다. 실제 답변 텍스트와 토큰·모델 메타데이터가 함께 들어 있는 구조다. 파서는 `StrOutputParser()`, 텍스트 속성은 `.content`다.

**이해 잘못한 부분 / 피드백**

제시한 출력물은 rewrite_chain의 마지막 컴포넌트인 모델(ChatOpenAI 등 LangChain ChatModel)이 호출 결과로 반환한 AIMessage 객체 전체를 그대로 출력했을 때 나오는 모습이다.

**6장 1강 : 평가셋 구성과 검색 지표 (1)**

RAG 평가 지표, 검색 품질 지표:

1. Context Precision (문맥 정밀도)
2. Context Recall (문맥 재현율)

> 교재 · 6장 1강

### 1. 용어 해독 공식 (2글자 쪼개기)

- 앞 글자 (`T` / `F`) = 정답 여부 (실제와 일치하는가?)
  - T (True): 모델의 예측이 맞음 (정답)
  - F (False): 모델의 예측이 틀림 (오답)
- 뒷 글자 (`P` / `N`) = 모델의 예측값 (모델이 뭐라고 찍었는가?)
  - P (Positive): 모델이 "맞다 / 해당된다 / 관련 문서다 (1)"라고 예측
  - N (Negative): 모델이 "아니다 / 해당 안 된다 / 무관한 문서다 (0)"라고 예측

### 2. 4가지 조합 상세 해석 (RAG 검색 기준 예시)

질문에 대해 관련 있는 문서(정답)를 찾아내는 검색기로 비유하면 다음과 같다.

| 약어 | 풀네임         | 모델 예측            | 실제 정답 | 의미 및 상황 (RAG 검색 기준)                                                   |
| ---- | -------------- | -------------------- | --------- | ------------------------------------------------------------------------------ |
| TP   | True Positive  | Positive (관련 있음) | 관련 있음 | 제대로 찾음: 관련 문서를 정확히 검색해 옴 (가장 이상적)                        |
| FP   | False Positive | Positive (관련 있음) | 관련 없음 | 잘못 찾음 (오탐/노이즈): 관련 없는 쓰레기 문서를 관련 있다고 가져옴 (1종 오류) |
| FN   | False Negative | Negative (관련 없음) | 관련 있음 | 놓침 (미탐/누락): 꼭 필요한 정답 문서를 관련 없다고 버림 (2종 오류)            |
| TN   | True Negative  | Negative (관련 없음) | 관련 없음 | 제대로 걸러냄: 관련 없는 문서를 정확히 제외함                                  |

### 3. 실무 핵심 평가 지표와의 연결

- 정밀도 (Precision) = $\frac{TP}{TP + FP}$
  - 모델이 "관련 있다(P)"고 가져온 것들 중 진짜 정답(TP)의 비율 (노이즈가 얼마나 없는가?)
- 재현율 (Recall) = $\frac{TP}{TP + FN}$
  - DB에 있는 전체 진짜 정답(TP + FN) 중 모델이 놓치지 않고 찾아낸 비율 (누락이 얼마나 없는가?)

한 줄 요약: 뒤 글자(P/N)는 '모델의 예측', 앞 글자(T/F)는 '그 예측의 정답 여부'를 뜻하며, 검색에서는 노이즈를 줄이려면 FP를 낮추고(Precision↑), 정답 누락을 막으려면 FN을 낮춰야(Recall↑) 한다.

통계학의 가설검정(귀무가설 $H_0$: 아무 일 없다 / 정상이다 / 관련 없다)에서 유래한 용어로, 앞서 본 FP(False Positive)와 FN(False Negative)의 통계학적 이름이다.
가장 확실한 암기법은 "양치기 소년" 비유다. 거짓으로 양성이 뜨는 것(FP, 늑대가 없는데 왔다고 소리침)이 1종 오류, 실제 양성을 놓치는 것(FN, 진짜 늑대가 왔는데 못 보고 지나침)이 2종 오류다. 실무에서는 두 오류의 치명도가 도메인마다 다르기 때문에 어느 쪽을 더 엄격하게 막을지 기준선(Threshold)을 조절해야 한다.

### 4. 1종 오류 vs 2종 오류 정의

- **1종 오류** (Type I Error) = FP (False Positive / 오탐 / 위양성)
  - 정의: 실제로는 음성(거짓/정상/무관)인데, 모델이나 검사가 양성(참/이상/관련)이라고 잘못 판정하는 오류
  - 가설검정 관점: 귀무가설($H_0$: 효과 없다/정상이다)이 참인데도 이를 기각하는 오류 (유의수준 $\alpha$)
- **2종 오류** (Type II Error) = FN (False Negative / 미탐 / 위음성)
  - 정의: 실제로는 양성(참/이상/관련)인데, 모델이나 검사가 음성(거짓/정상/무관)이라고 놓치는 오류
  - 가설검정 관점: 귀무가설($H_0$)이 거짓인데도 기각하지 못하고 넘어가는 오류 ($\beta$, 검정력 $= 1 - \beta$)

### 5. 도메인별 상황 비교

| 구분                | 1종 오류 (Type I Error / FP)                             | 2종 오류 (Type II Error / FN)                          |
| ------------------- | -------------------------------------------------------- | ------------------------------------------------------ |
| 통계·판정 의미      | 없는 것을 있다고 착각 (헛경보)                           | 있는 것을 없다고 놓침 (놓침)                           |
| RAG 검색 기준       | 관련 없는 노이즈 문서를 정답이라고 가져옴                | 꼭 필요한 핵심 정답 문서를 누락함                      |
| 스팸 메일 필터      | 정상 업무 메일을 스팸함으로 잘못 분류 (치명적)           | 스팸 메일을 걸러내지 못하고 받은편지함으로 통과시킴    |
| 암 진단 / 보안 관제 | 건강한 사람을 암 환자로 오진 (추가 정밀검사로 확인 가능) | 실제 암 환자나 해킹 공격을 정상으로 방치 (매우 치명적) |

### 6. 실무 트레이드오프와 제어 방향

- 1종 오류(FP)와 2종 오류(FN)는 시소 관계에 있어 한쪽을 극단적으로 줄이면 다른 한쪽이 늘어난다
  - RAG에서 1종 오류(FP)가 문제일 때 (환각·노이즈 심각): `Score Threshold`를 엄격하게 높이고 Re-ranker를 도입해 정밀도(Precision)를 확보한다
  - RAG에서 2종 오류(FN)가 문제일 때 (정보 누락 심각): `Top-k`를 늘리고 하이브리드 검색(BM25 + Vector)을 사용해 재현율(Recall)을 확보한다

한 줄 요약: 1종 오류(FP)는 '없는 걸 있다고 착각하는 헛경보(노이즈)'이고, 2종 오류(FN)는 '있는 걸 없다고 놓치는 미탐(누락)'이며, 서비스 성격에 따라 어느 오류를 더 치명적으로 볼지 결정해 임계값(Threshold)을 조절해야 한다.

### 7. RAG 평가셋 (Evaluation Set / Golden Dataset) 개념

**평가셋**(Golden Dataset)은 검색(Retrieval)과 생성(Generation) 파이프라인의 성능을 감이 아닌 정량적 수치로 객관화·추적하기 위해 사전에 구축해 두는 표준 테스트 데이터셋이다.
청킹 전략, 임베딩 모델, 프롬프트, Reranker 등을 변경할 때마다 성능 개선 여부를 검증하는 기준선(Baseline) 역할을 한다.

### 8. 평가셋의 3대 핵심 요소 (Triplet 구조)

RAG 파이프라인의 각 단계를 분리해서 채점하려면 아래 세 가지 데이터가 하나의 세트로 매핑되어야 한다.

- 질문 (Question / Query):
  - 실제 사용자가 입력할 법한 자연어 질의
  - 단순 키워드형, 의미 탐색형, 복합 조건형, 부정(답변 불가) 질의 등 다양한 난이도와 유형을 균형 있게 포함해야 한다
- 근거 문서 (Context / Ground Truth Context):
  - 해당 질문에 답하기 위해 검색기(Retriever)가 벡터 DB에서 반드시 찾아내야 하는 원본 문서 청크(Chunk) 또는 문서 ID
  - 검색 단계(Retrieval) 평가 지표(Recall@K, Precision@K, MRR, Context Recall 등)를 산출하는 기준
- 정답 (Ground Truth / Reference Answer):
  - 근거 문서를 바탕으로 LLM이 최종적으로 생성해야 하는 모범 답안 텍스트
  - 생성 단계(Generation) 평가 지표(Faithfulness, Answer Relevancy, Answer Correctness 등)를 산출하는 기준

### 9. 평가 요소별 검증 파이프라인 매핑

| 평가셋 요소                 | 평가 대상 모듈           | 주요 검증 질문                                       | 대표 평가 프레임워크 지표 (RAGAS 등)        |
| --------------------------- | ------------------------ | ---------------------------------------------------- | ------------------------------------------- |
| Question + Context          | 검색기 (Retriever)       | 필요한 근거 문서를 빠짐없이 상단에 가져왔는가?       | Context Recall, Context Precision, Hit Rate |
| Question + Context + Answer | 생성기 (Generator / LLM) | 가져온 문서 내용에만 근거해 사실대로 답했는가?       | Faithfulness (충실도), Answer Relevancy     |
| Ground Truth + Answer       | 전체 파이프라인 (E2E)    | 최종 답변이 모범 답안과 의미·사실 면에서 일치하는가? | Answer Correctness, Semantic Similarity     |

한 줄 요약: RAG 평가셋은 '질문(Question) - 근거 문서(Context) - 모범 답안(Ground Truth)'의 3요소 쌍으로 구성되며, 이를 통해 검색기의 탐색 성능과 생성기의 답변 품질을 분리해 정량적으로 채점할 수 있다.

### 10. 검색 단계 평가 지표 (Retrieval Metrics) 개념

검색기(Retriever)가 전체 DB에서 정답 근거 문서를 누락 없이 찾아왔는지(포괄성)와 불필요한 노이즈 문서를 섞지 않았는지(순도)를 정량화한 지표다.

### 11. 정밀도 vs 재현율

- **Context Precision** (문맥 정밀도):
  - 정의: 검색기가 반환한 상위 $K$개 문서 중 실제 정답 근거 문서가 차지하는 비율 ($\frac{TP}{TP + FP}$)
  - 역할: 검색 결과의 순도(Quality) 측정 (노이즈가 얼마나 적은가)
- **Context Recall** (문맥 재현율):
  - 정의: 전체 DB에 존재하는 실제 정답 문서 중 검색기가 누락 없이 찾아낸 비율 ($\frac{TP}{TP + FN}$)
  - 역할: 검색의 포괄 범위(Coverage) 측정 (정답 누락이 얼마나 없는가)

### 12. 조화 평균: F1-Score

- 트레이드오프(Trade-off) 관계:
  - `Top-k`를 무작정 늘리면 정답을 놓칠 확률은 줄어 재현율(Recall)은 상승하지만, 무관한 노이즈 문서가 대거 유입되어 정밀도(Precision)는 하락한다
- 산술평균 대신 조화평균(Harmonic Mean)을 쓰는 이유:
  - 단순 산술평균은 한쪽 지표가 바닥이어도 다른 쪽이 높으면 평균 점수가 양호해 보이는 착시(왜곡)가 발생한다
  - 조화평균은 두 값 중 더 작은 값에 큰 패널티(가중치)를 부여하므로, 정밀도와 재현율 중 하나라도 결함이 있으면 전체 점수를 엄격하게 낮춘다
- 계산 수식:

$$F_1 = 2 \times \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$

### 13. 지표 비교 및 성능 판정 기준

| 측정 케이스        | 정밀도 (Precision) | 재현율 (Recall) | 단순 산술평균 | F1-Score (조화평균) | 수치 해석 및 모델 상태                                             |
| ------------------ | ------------------ | --------------- | ------------- | ------------------- | ------------------------------------------------------------------ |
| 극단적 편향 검색기 | 0.10               | 0.90            | 0.50          | 0.18                | 심각한 정밀도 결함(노이즈 과다)을 감지하여 낮은 점수로 엄격히 판정 |
| 균형 잡힌 검색기   | 0.80               | 0.80            | 0.80          | 0.80                | 두 지표 간 밸런스가 유지되어 높은 종합 성능으로 산출               |

한 줄 요약: 정밀도(순도)와 재현율(포괄성)은 서로 트레이드오프 관계에 있으므로, 한쪽 지표의 극단적 결함을 숨기지 않고 엄격히 패널티를 주는 조화평균(F1-Score)을 통해 검색기의 균형 성능을 평가한다.

**이해 잘못한 부분 / 피드백**

제시한 내용은 정밀도, 재현율의 개념과 조화평균(F1-Score)을 사용하는 수학적·실무적 이유를 매우 정확하게 정리했다.
다만 RAG 실무에서는 단순 집합 비율 기반의 Precision/Recall에서 한 단계 더 나아가 '순위(Rank) 가중치'를 반영한 지표를 함께 본다는 점이 핵심이다. 같은 `Precision@5 = 0.2`라도 정답 문서가 1등에 배치된 것과 5등에 배치된 것은 LLM의 Lost in the Middle 현상과 직결된다.
실무에서는 정답 문서가 상위에 위치할수록 높은 점수를 주는 지표를 결합해 검색기 성능을 최종 판정한다.
순위 지표에는 **MRR**(Mean Reciprocal Rank), MAP(Mean Average Precision), NDCG가 있다.

**6장 2강 : 생성 지표와 실패 원인 분석 (1)**

> 교재 · 6장 2강

### 1. 생성 단계 평가 지표 (Generation Metrics)

LLM이 최종 출력한 텍스트가 주어진 근거 문맥(Context)에 충실한지, 그리고 사용자의 질문(Question) 의도에 부합하는지를 검증하는 지표다.

### 사실성 / 충실도 / 신뢰도 (Faithfulness)

- 개념: 생성된 답변의 모든 내용이 검색기가 전달한 '근거 문서(Context)' 내부 정보에만 기반하고 있는지 평가한다
- 측정 목적: 문서에 없는 외부 지식을 끌어오거나 허위 사실을 지어내는 환각(Hallucination) 탐지
- 판정 기준: 최종 답변을 개별 주장(Claim/Statement) 단위로 분해한 뒤, 근거 문서에서 논리적으로 추론·증명 가능한 문장의 비율을 계산한다

$$\text{Faithfulness} = \frac{\text{근거 문서로 증명 가능한 주장 수}}{\text{답변 내 전체 주장 수}}$$

**Faithfulness**는 문서 밖의 거짓말을 하지 않았는지를 재는 축이다.

### 답변 관련성 (Answer Relevance)

- 개념: 생성된 답변이 사용자가 입력한 '질문(Question)'의 핵심 의도에 정확히 초점을 맞추고 있는지 평가한다
- 측정 목적: 사실 여부와 관계없이 질문의 핵심을 비껴가거나 불필요한 사족을 늘어놓는 동문서답 오류 검출
- 판정 기준: 문장 길이나 유창성이 아닌, 질문에 대한 직접적 해답 제공 여부 평가 (RAGAS 기준: 답변으로부터 역생성한 가상 질문들과 원본 질문 간의 임베딩 유사도 평균으로 산출)

**Answer Relevance**는 질문에 동문서답하지 않았는지를 재는 축이다.

### 2. RAG 파이프라인 실패 원인 분석 (오류 진단)

최종 답변 품질이 떨어졌을 때, '필요한 문서를 못 찾은 것(검색 실패)'인지 '문서는 잘 가져왔는데 LLM이 잘못 읽은 것(생성 실패)'인지 먼저 분리해야 올바른 튜닝 방향을 정할 수 있다.

### 검색 실패 vs 생성 실패 비교

| 구분      | 검색 실패 (Retrieval Failure)                                                            | 생성 실패 (Generation Failure)                                                        |
| --------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 발생 원인 | 청킹(Chunking) 전략 오류, 임베딩 모델 부적합, 부적절한 Top-k / Score Threshold           | 프롬프트 지시문 모호성, 긴 문맥 집중력 저하(Lost in the Middle), LLM 추론 한계        |
| 주요 증상 | 전달된 Context 자체에 질문에 답할 핵심 근거가 누락됨                                     | Context에 정답이 명확히 들어있음에도 답변에서 왜곡·누락·환각 발생                     |
| 개선 방향 | 청크 크기/오버랩 재설계, 하이브리드 검색(BM25+Vector) 도입, Re-ranking 및 쿼리 변환 적용 | 시스템 프롬프트 제약 강화("문서 외 추론 금지"), 맥락 압축(Compression), 상위 LLM 교체 |

### 환각 유형과 지표 영향

- 외부 지식 유입에 의한 환각 (**Extrinsic Hallucination**): 근거 문서에 없는 내용을 LLM의 사전 학습(Pre-training) 파라미터 기억에 의존해 단정적으로 서술 → 사실성(Faithfulness) 점수 급락
- 논리 왜곡에 의한 환각 (**Intrinsic Hallucination**): 근거 문서 내에 존재하는 A 조건과 B 조건을 잘못 섞어 틀린 인과관계·수치·예외 규칙으로 왜곡 서술 → 문맥 내 단어를 썼더라도 문장 단위 검증에서 사실성(Faithfulness) 감점

한 줄 요약: 생성 평가는 '문서 밖의 거짓말을 안 했는가(Faithfulness)'와 '질문에 동문서답하지 않았는가(Answer Relevance)'의 두 축으로 측정하며, 오류 발생 시 근거 문서(Context) 내 정답 유무를 먼저 확인해 검색 실패와 생성 실패를 분리 진단해야 한다.

**이해 잘못한 부분 / 피드백**

제시한 내용은 RAG 생성 단계의 핵심 평가 지표(Faithfulness, Answer Relevance)와 장애 발생 시 원인 분리 원칙(검색 실패 vs 생성 실패)을 매우 정확하고 체계적으로 정리했다.
다만 실무에서 평가 지표를 해석할 때 반드시 경계해야 할 점은 Faithfulness(사실성)와 Answer Relevance(답변 관련성)는 서로 보완 관계일 뿐, 하나가 높다고 정답이 보장되지 않는다는 것이다. 예를 들어 모델이 "문서에 해당 정보가 없습니다"라고 답하면 근거 문서를 벗어나지 않았으므로 Faithfulness = 1.0이 나오지만, 실제 문서에 정답이 있었다면 질문 해결에 실패했으므로 Answer Relevance나 Answer Correctness는 바닥을 치게 된다. 또한 RAGAS 등에서 Answer Relevance는 생성된 답변으로부터 역으로 질문을 생성(Reverse Question Generation)한 뒤 원래 질문과의 코사인 유사도를 재는 방식으로 계산된다는 점도 함께 기억하면 좋다.

### 3. 사실성 / 충실도 (Faithfulness) 낮을 때 개선 방법

문서에 없는 내용을 지어내거나(환각), 문서의 조건·수치를 왜곡해서 답변할 때 적용하는 처방이다.

- 시스템 프롬프트 제약 조건 강화 (Grounding 강제):
  - "반드시 제공된 `[Context]` 내의 사실만 사용해 답변하고, 근거가 부족하면 추측하지 말고 '제공된 문서에서 관련 정보를 찾을 수 없습니다'라고 답변하라"는 부정 제약(Negative Constraint)을 명시한다
- 근거 인용(Citation) 강제 출력:
  - 답변 문장 끝에 `[문서 1]`, `[조항 3]` 등 출처 태그를 반드시 달도록 강제하여 LLM이 사전 학습 지식을 몰래 섞지 못하게 억제한다
- 디코딩 파라미터(Temperature) 하향 조정:
  - 창의적 문장 생성을 차단하기 위해 Temperature = 0.0 ~ 0.1로 고정하여 가장 확률 높은 사실 기반 토큰만 선택하도록 유도한다
- 맥락 압축 (Contextual Compression) 적용:
  - 문서 내 불필요한 배경 설명이나 다른 조건 조항을 사전에 잘라내어, LLM이 서로 다른 조건을 섞어 왜곡하는 현상(Intrinsic Hallucination)을 방지한다
- LLM 모델 업그레이드 (지시 이행력 강화):
  - 컨텍스트 준수 능력(Instruction Following)과 긴 문맥 독해력이 뛰어난 상위 모델로 교체한다

### 4. 답변 관련성 (Answer Relevance) 낮을 때 개선 방법

답변이 사실이긴 하나 질문 의도를 빗나가거나, 불필요한 사족이 많아 동문서답할 때 적용하는 처방이다.

- 출력 형식 및 페르소나 구조화 (Few-shot / Template):
  - 질문 유형에 맞춰 답변 구조를 제한한다 (예: "결론을 첫 문장에 두괄식으로 제시하고, 핵심 근거 3줄 이내로 요약하라")
  - 원하는 응답 톤과 간결함을 보여주는 Few-shot 예시 1~2개를 프롬프트에 삽입한다
- 질의 재작성 (Query Rewriting) 도입:
  - 사용자의 모호하거나 구어체로 된 질문을 검색·생성하기 좋은 명확한 표준 질의로 한 번 변환한 뒤 LLM에 전달한다
- 불필요한 서론·사족 제거 지시:
  - "질문과 직접 관련 없는 배경 설명, 인사말, 일반론은 생략하고 핵심 해결책만 작성하라"는 포맷 제약을 추가한다
- 앞단 검색 품질(Retriever / Reranker) 재점검:
  - LLM이 엉뚱한 답을 하는 이유 자체가 질문과 핀트가 어긋난 문서만 Context로 받았기 때문일 수 있으므로, Top-k 축소 및 Re-ranker 적용으로 핵심 문서만 남긴다

### 5. 지표별 개선 처방 요약표

| 하락 지표                      | 주요 원인                                      | 프롬프트 / 파라미터 처방                                                                         | 파이프라인 / 모델 처방                                                                              |
| ------------------------------ | ---------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| Faithfulness (사실성)          | 외부 사전지식 개입, 문맥 내 조건 왜곡 (환각)   | 근거 외 추론 금지 및 "모른다" 답변 강제 / 문장별 출처(Citation) 표기 강제 / Temperature = 0 설정 | 맥락 압축(Compression)으로 노이즈 제거 / 지시 이행력(Instruction Following)이 높은 상위 LLM 교체    |
| Answer Relevance (답변 관련성) | 동문서답, 불필요한 장황함, 질문 의도 파악 실패 | 두괄식 요약·출력 포맷 강제 / 모범 답변 Few-shot 예시 추가 / 배경 설명·사족 금지 지시             | 질의 재작성(Query Rewriting)으로 의도 명확화 / Re-ranker 도입 및 Top-k 축소로 핀트 어긋난 문서 차단 |

한 줄 요약: Faithfulness가 낮으면 '문서 외 추론 금지·Temperature 0·출처 강제'로 환각을 틀어막고, Answer Relevance가 낮으면 '출력 포맷 구조화·Few-shot·질의 재작성'으로 질문 의도에 직결되는 핵심만 답하도록 교정한다.

**이해 잘못한 부분 / 피드백**

생성 단계 지표(Faithfulness, Answer Relevance)가 낮을 때 1차적으로 프롬프트와 LLM 모델을 손보는 방향은 정확하다.
다만 실무에서 간과하기 쉬운 점은 모든 생성 지표 하락을 프롬프트나 모델 탓으로만 돌리면 안 된다는 것이다. Faithfulness가 낮을 때는 프롬프트 제약 조건과 Temperature 조정이 직빵이지만, Answer Relevance가 낮을 때는 프롬프트 문제보다 '1차 검색기(Retriever)가 질문과 어긋난 문서를 가져왔거나, 너무 긴 청크가 들어가 핵심을 흐린 경우'가 훨씬 많다. 두 지표의 하락 원인이 다르므로 처방도 분리해서 적용해야 한다.
