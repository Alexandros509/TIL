RAG 파이프라인 설계

- **RAG**: Retrieval Augmented Generation (검색 증강 생성)

한계 존재: LLM 모델의 한계

1. 지식 컷오프 - 학습 시점의 지식으로 고정. 그 이후의 지식 X
2. 환각 - 지식의 부재로 발생

> 교재 · 1장 1강

- LLM은 학습된 데이터 범위 안에서 통계적으로 그럴듯한 문장을 이어 붙임 → 학습 시점 이후 최신 정보·비공개 문서는 모르고, 잘못된 사실을 지어내기도 함
- **지식 컷오프**(Knowledge Cutoff): 사전 학습이 끝난 기준 날짜 이후의 사건·최신 데이터를 기억하지 못하는 한계
- **환각**(Hallucination): 답을 모를 때 공백을 채우려고 사실이 아닌 내용을 정교하고 확신에 찬 어조로 왜곡해 출력하는 현상

검색 - 외부 지식 검색, 임베딩 모델 (실수 벡터)

증강 - 프롬프트

생성 - LLM 답변

> 교재 · 1장 1강

- RAG = 답변 생성 전에 외부 데이터베이스에서 관련 근거를 먼저 찾아 LLM에 제공 → '암기식 시험'을 '오픈북 시험'으로 바꾸는 것
- 단순 LLM 호출: 모델 내부 가중치(기억)에만 의존해 답변 생성
- RAG 파이프라인: 관련 문서 탐색(Retrieve) → 확보한 근거를 프롬프트에 주입 → 신뢰성 높은 답변 생성(Generate)

| 비교 항목 | 단순 LLM 호출 | RAG 기반 생성 |
| --- | --- | --- |
| 정보의 최신성 | 학습 종료 시점(컷오프)에 머무름 | 최신 문서를 즉시 검색하여 반영 가능 |
| 비공개 사내 데이터 | 학습되지 않아 답변 불가 | 보안 문서, 사내 규정 문서 직접 참조 가능 |
| 답변의 근거 제시 | 출처 추적이 불가능함 | 인용한 원본 문서 출처 명시 가능 |
| 환각 발생률 | 모르는 질문에 환각 발생 가능성 높음 | 문서 내 사실에 기반하므로 환각 억제 |

- 실습: `init_chat_model`(벤더 비종속 LLM 생성 함수) → `StrOutputParser` 체인으로 단순 호출

~~~python
# test.ipynb
import os
from langchain.chat_models import init_chat_model
from langchain_core.output_parsers import StrOutputParser

model = init_chat_model(
    model_provider="openai",
    model="gpt-6-luna",
    api_key = os.getenv("OPENAI_API_KEY")
)

parser = StrOutputParser()

chain = model | parser

response = chain.invoke([("오늘 날짜는?")])
print(response)
~~~

~~~text
오늘은 2026년 11월 12일입니다.
~~~

- 외부 문서를 프롬프트의 `{context}` 변수에 주입해 사실 기반 답변 유도

~~~python
# 외부 문서(Context)를 주입받을 수 있는 RAG 전용 프롬프트 템플릿을 정의합니다.
rag_prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        "당신은 제공된 [참고 문서]의 내용에만 근거하여 정확하게 답변하는 전문 튜터입니다.\n"
        "문서에 나와 있지 않은 내용은 절대로 지어내지 말고 모른다고 답변하세요.\n\n"
        "[참고 문서]:\n{context}"
    ),
    ("user", "{question}")
])

# RAG 체인을 조립합니다
rag_chain = rag_prompt | model | parser

# 데이터베이스나 검색기로부터 찾아왔다고 가정한 외부 최신 문서 데이터입니다.
retrieved_context = """
[공지] 2026학년도 스파르타대학교 컴퓨터공학과 봄 축제 안내
- 일시: 2026년 5월 14일(목) ~ 5월 15일(금)
- 장소: IT융합관 앞 잔디광장
- 초청 아티스트: 뉴진스, 악동뮤지션
- 유의사항: 학생증 지참 필수
"""

# 질문과 함께 검색된 문맥(context)을 모델에 전달합니다.
rag_response = rag_chain.invoke({
    "context": retrieved_context,
    "question": "2026년 스파르타대학교 컴퓨터공학과 1학기 축제 개최일과 초청 가수를 알려줘."
})

print("=== [RAG 기반 생성 결과] ===")
print(rag_response)
~~~

~~~text
=== [RAG 기반 생성 결과] ===
개최일: 2026년 5월 14일(목) ~ 5월 15일(금)
초청 아티스트: 뉴진스, 악동뮤지션
~~~

- 같은 질문을 단순 호출하면 모델이 학습 기준 시점 이후라 축제 정보를 알려줄 수 없다고 답함 (지식 컷오프 확인)

**파인 튜닝** ( Fine-tuning )

- 기존 LLM 파라미터는 그대로 유지
- 새로 추가된 작은 파라미터만 학습 → LoRA

> 교재 · 1장 1강

- 파인튜닝 = 모델의 '말투나 행동 양식'을 체화, RAG = 모델에게 '새로운 지식 서가'를 주입 → 문제 성격과 데이터 업데이트 주기로 선택
- 파인튜닝: 대량의 질의-응답 데이터셋으로 모델 파라미터(가중치)를 미세하게 재학습시키는 기법
- RAG: 모델 파라미터는 그대로 두고, 검색 시스템을 연결해 외부 데이터를 실시간 주입하는 아키텍처

| 비교 지표 | RAG (검색 증강 생성) | 파인튜닝 (미세조정) |
| --- | --- | --- |
| 지식 갱신 주기 | 실시간 (새 문서를 DB에 추가하는 즉시 반영) | 주기적 재학습 필요 (모델 재학습 비용 발생) |
| 구축 비용 | 상대적으로 저렴하고 인프라 관리가 용이함 | GPU 학습 자원과 데이터 구축 비용이 큼 |
| 적합한 목표 | 최신 팩트 전달, 사내 규정 조회, 환각 방지 | 특정 어조·화법 습득, 고정된 출력 포맷 준수 |
| 출처 제공 여부 | 답변에 참조한 문서의 제목/페이지 표기 가능 | 모델 내부 기억이므로 출처 확인 불가 |

- RAG를 선택해야 하는 경우
  - 매주/매월 제품 가격표나 사내 취업 규칙이 변경되는 경우
  - 사용자가 답변 신뢰도를 위해 근거 문서 링크를 요구하는 경우
- 파인튜닝을 선택해야 하는 경우
  - 금융·의료 전문 용어의 독특한 문체나 특정 페르소나를 이식해야 하는 경우
  - 복잡한 JSON 스키마 규격을 오류 없이 엄격하게 준수해야 하는 경우

**1장 2강 : RAG 파이프라인 5단계 구조 (1)**

사용자 질의

외부 지식 저장소 ( Vector DB )

> 교재 · 1장 2강

- RAG = '시험 전 공부하기(인덱싱)' + '시험 당일 문제 풀기(질의)' 두 단계
- **인덱싱**(Indexing): 질문 전에 외부 문서를 수집하고, 쪼개고, 숫자로 변환해 검색 가능한 저장소에 저장
- **질의**(Query): 질문이 들어오면 관련성 높은 문서를 찾아 모델에 전달하고 최종 답변 생성

| 구분 | 인덱싱 단계 (Indexing) | 질의 단계 (Query) |
| --- | --- | --- |
| 작업 시점 | 사용자의 질문이 발생하기 전 (배치/사전 작업) | 사용자가 질문을 입력한 즉시 (실시간 작업) |
| 포함 단계 | 1단계 수집 → 2단계 분할 → 3단계 임베딩·저장 | 4단계 검색 → 5단계 생성 |
| 비유 | 시험 치기 전 참고서를 읽고 요약 노트를 만들어 두는 과정 | 시험 문제를 읽고 요약 노트에서 답을 찾아 서술하는 과정 |

- 5단계: 수집 → 분할 → 임베딩 → 검색 → 생성 (앞 단계 결과가 다음 단계 입력)
  1. 문서 수집(Loading): PDF, 웹페이지, 내부 DB 등 원본 데이터를 파이썬이 다룰 수 있는 텍스트로 추출
  2. 문서 분할(Chunking): 긴 문서를 한 번에 이해하기 좋은 작은 단위(청크)로 자름
  3. 임베딩 및 저장(Embedding & Storing): 텍스트 조각을 의미 기반 숫자 배열(벡터)로 변환해 벡터 DB에 저장
  4. 검색(Retrieval): 질문 기준으로 벡터 유사도가 가장 높은 청크를 찾아옴
  5. 생성(Generation): 검색된 청크를 프롬프트 문맥(context)으로 주입해 사실에 입각한 답변 유도

**청크** ( Chunk )

- 긴 문서를 검색하기 쉽도록 일정한 규칙에 따라 분할한 텍스트 조각

ETL 과정을 통한 적재

- Extract : txt, pdf, html
- Transform : 데이터 전처리, 청킹, 임베딩
- Load : 벡터 저장소(Vector DB)에 적재

- 실습: ETL 전 과정 (분할 → 임베딩 → 메모리 벡터 저장소 → 검색 → 생성)

~~~python
# 02.ipynb
# ETL (인덱싱, 청킹, 임베딩, 저장)
import os
from langchain_text_splitters import RecursiveCharacterTextSplitter, CharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_core.vectorstores import InMemoryVectorStore
~~~

~~~python
raw_text= """ 
마하반야바라밀다심경

관자재보살 행심반야바라밀다시 조견오온개공 도일체고액 

사리자 색불이공 공불이색 색즉시공 공즉시색

수상행식 역부여시 사리자 시제법공상

불생불멸 불구부정 부증불감 시고 공중무색 무수상행식

무안이비설신의 무색성향미촉법 무안계 내지 무의식계

무무명 역무무명진 내지 무노사 역무노사진 무고집멸도

무지역무득 이무소득고 보리살타 의반야바라밀다고

심무가애 무가애고 무유공포 원리전도몽상 구경열반

삼세제불 의반야바라밀다고 득아뇩다라삼먁삼보리

고지반야바라밀다 시대신주 시대명주 시무상주

시무등등주 능제일체고 진실불허 고설 반야바라밀다주

즉설주왈

아제아제 바라아제 바라승아제 모지 사바하
"""


# 청킹
text_splitter = RecursiveCharacterTextSplitter(
    # separator="",
    chunk_size=90,
    chunk_overlap=20
)

split_docs = text_splitter.create_documents([raw_text])

len(split_docs)
~~~

~~~text
4
~~~

~~~python
for i, doc in enumerate(split_docs,1):
    print(f"[청크: {i}] {doc.page_content}")
~~~

~~~python
# 임베딩 - 문장 -> 실수 벡터
embedding_model = OpenAIEmbeddings(
    model="text-embedding-3-small", 
    api_key=os.getenv("OPENAI_API_KEY_TUTOR")
    )

vector_store = InMemoryVectorStore.from_documents(
    documents=split_docs,
    embedding=embedding_model
)
~~~

~~~python
# 검색 (Retrieval)
retriever = vector_store.as_retriever(search_kwargs={"k":2})

user_query = "마하반야바라밀다심경이 뜻이 뭐야?"

retrieved_results = retriever.invoke(user_query)

for i , doc in enumerate(retrieved_results, 1):
    print(f"[{i}번] {doc.page_content} ")
~~~

~~~python
from langchain.chat_models import init_chat_model
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

model = init_chat_model(
    model_provider="openai",
    model="gpt-6-luna",
    api_key=os.getenv("OPENAI_API_KEY_TUTOR")
)

prompt = ChatPromptTemplate.from_messages([
    ("system","제공된 [참고문서]의 내용에만 근거하여 답변하세요. [참고문서]에서 없는 내용에는 모른다라고 답변하세요.\n\n[참고문서]:\n{context}"),
    ("user","{question}")
])

parser = StrOutputParser()

chain = prompt | model | parser
response = chain.invoke({
    "context": retrieved_results[0].page_content,
    "question": user_query
})

print(response)
~~~

~~~text
참고문서에는 「마하반야바라밀다심경」의 뜻에 대한 설명이 없어 모릅니다. 본문 구절만 제시되어 있습니다.
~~~

- 분할 결과 4청크, `k=2` 검색 시 1번(제목 포함 청크)·4번 청크 반환
- 참고문서에 뜻 설명이 없으므로 「모른다」로 답함 → 프롬프트 지시로 환각 억제

> 교재 · 1장 2강

- 단계별 품질 병목: 어느 한 단계라도 어긋나면 최종 답변 품질·신뢰도 하락 → 오류 시 5단계 중 결함 지점을 추적·진단
  - 수집 결함: 표가 깨지거나 글자가 누락된 채로 읽으면 후속 단계 전체가 잘못된 데이터를 다룸
  - 분할 결함: 문맥 없이 단순 길이로 자르면 문장 중간이 끊겨 의미 파악 불가
  - 임베딩 결함: 의미적 유사성을 올바르게 계산하지 못해 엉뚱한 거리 값 도출
  - 검색 결함: 질문 의도와 동떨어진 청크가 전달되어 모델에 잘못된 참고서가 들어감
  - 생성 결함: 정확한 참고 문서를 주었는데도 문서를 무시하고 지어낸 답변(환각) 출력

| 단계 | 주요 병목 원인 | 최종 결과에 미치는 영향 |
| --- | --- | --- |
| 1. 문서 수집 | 스캔본 인식 오류, 표/서식 깨짐 | 왜곡된 데이터가 시스템 전체로 전파 |
| 2. 문서 분할 | 청크 크기 과소/과대, 문맥 단절 | 주어·목적어 유실로 핵심 정보 손실 |
| 3. 임베딩 | 도메인 특화 용어 의미 반영 실패 | 질문과 문서 조각 간의 의미 매칭 실패 |
| 4. 검색 | 저품질 청크 검색, 검색 개수(k) 부족 | 모델에게 잘못된 참고 자료 전달 |
| 5. 생성 | 프롬프트 지시 불이행, 환각 현상 | 제공된 근거를 무시한 거짓 답변 생성 |

**1장 3강 : 임베딩과 벡터 표현 (1)**

> 교재 · 1장 3강

- **임베딩**(Embedding): 단어·문장의 의미를 다차원 공간의 좌표(숫자 배열)로 변환 → 텍스트 간 의미적 유사도 계산의 수학적 기반
- 의미 공간(Semantic Space)
  - 컴퓨터는 문자 자체를 계산할 수 없음 → 모든 글자를 숫자로 변환
  - 의미가 유사한 문장은 다차원 공간에서 가까운 좌표에 위치
  - 단어·문장 간 관계를 거리와 각도로 측정 가능
- **차원**(Dimension): 문장의 의미를 세부적으로 측정·분류하는 기준 축의 총개수
  - `text-embedding-3-small`: 문장 1개 → 1,536개의 실수(Float) 배열

| 구분 | 1차원 수직선 | 2차원 평면 | 고차원 의미 공간 (1,536차원) |
| --- | --- | --- | --- |
| 표현 형태 | 단일 숫자 (x) | 좌표 쌍 (x, y) | 1,536개의 실수 배열 ([v1, v2, …, v1536]) |
| 표현력 | 크기 비교만 가능 | 평면 상의 거리 측정 | 문맥, 어조, 전문 용어 등 복합 의미 반영 |

**1장 4강 : 벡터 유사도 검색 원리 (1)**

의미 유사도 지식 조회

1. 유클리디안 거리 ( 수치 ↓ 유사, ↑ 유사 X )
2. **코사인 유사도** ( -1 ~ 1 , 1 유사 0 유사 X -1 반대 )
3. 내적 ( 방향 , 크기 )

> 교재 · 1장 4강

- **벡터 유사도**: 벡터 간 거리와 각도를 수학적으로 측정해 의미적 유사성을 판별하는 척도
- 코사인 유사도: 두 벡터 사이 각도의 코사인 값, 문서 길이 차이에 따른 왜곡이 없어 자연어 검색 표준
- 유클리디안 거리: 두 벡터 끝점 사이의 최단 직선거리, 0에 가까울수록 유사
- 내적(Dot Product): 방향과 크기를 동시에 반영, 단위 벡터로 정규화된 상태에서는 코사인 유사도와 같은 결과

| 척도명 | 주요 계산 대상 | 결과 범위 | 자연어 처리 활용 |
| --- | --- | --- | --- |
| 코사인 유사도 | 두 벡터 사잇각의 방향 일치도 | -1 ~ 1 | 문서 길이와 무관하게 주제 유사성 판단에 최적 |
| 유클리디안 거리 | 공간 상 두 점 사이의 직선거리 | 0 ~ ∞ | 물리적 거리 측정, 크기 차이가 중요한 데이터 |
| 내적 | 방향의 일치도 및 벡터의 절대적 크기 | -∞ ~ ∞ | 정규화된 임베딩 환경에서 초고속 유사도 계산 |

- 실습: numpy로 코사인·유클리디안 직접 구현 → 과일·동물 단어 임베딩 비교

~~~python
# similarity.ipynb
import numpy as np

"""
np.linalg.norm(): 유클리디언 정규화
"""

def cosine_similarity(v1,v2):
    return np.dot(v1,v2) / (np.linalg.norm(v1)*np.linalg.norm(v2))

def euclidean_similarity(v1,v2):
    return np.linalg.norm(np.array(v1)-np.array(v2))
~~~

**1장 5강 : 청킹 전략 (1)**

**청킹** ( Chunking )

- 문서 덩어리 임의 분해
- 컨텍스트 윈도우 크기의 한계
- 너무 긴 컨텍스트 → 의미적 유의성 ↓ → LLM의 답변 품질 ↓ → 청킹
- overlap 전후 맥락 파악하기 위한 일부 겹침
- 최적의 청킹 사이즈는 품질 평가를 통해서 조정

> 교재 · 1장 5강

- 청킹이 필요한 기술적 배경
  - 입력 창 크기 한계: 언어 모델·임베딩 모델은 한 번에 입력받을 수 있는 최대 토큰 수가 정해져 있음
  - 의미의 선명도 유지: 너무 긴 문서를 통째로 임베딩하면 여러 주제가 섞여 벡터의 의미 표현력 약화
  - 검색 효율성 극대화: 연관성 높은 핵심 문단만 선별해 전달 → 응답 속도·정확도 향상
- 분할 전략: 자르는 기준에 따라 고정 크기 / 재귀적 문자 / 의미론적 분할
- 고정 크기 분할(`CharacterTextSplitter`): 지정 글자 수로 기계 분할, 속도는 빠르나 단어·문맥 단절로 검색 정확도 저하

~~~python
# langchain_text_splitters 모듈에서 CharacterTextSplitter를 불러옵니다.
from langchain_text_splitters import CharacterTextSplitter

# 테스트를 위한 긴 문자열 데이터를 정의합니다.
sample_text = "청킹은 긴 문서를 작은 조각으로 나누는 과정입니다. 문맥 유지가 매우 중요합니다."

# 글자 수 15자를 기준으로 분할하는 고정 크기 분할기를 초기화합니다.
fixed_splitter = CharacterTextSplitter(
    separator="", # 특정 구분자 없이 글자 수 단위로 분할합니다.
    chunk_size=15, # 청크 1개의 최대 글자 수를 15자로 지정합니다.
    chunk_overlap=0 # 조각 간 겹치는 글자 수를 0으로 설정합니다.
)

# 텍스트를 분할하여 리스트 형태로 반환합니다.
fixed_chunks = fixed_splitter.split_text(sample_text)

# 생성된 청크를 순서대로 확인합니다.
for idx, chunk in enumerate(fixed_chunks):
    print(f"고정 청크 {idx + 1}: {chunk}")
~~~

~~~text

고정 청크 2: 으로 나누는 과정입니다. 문
고정 청크 3: 맥 유지가 매우 중요합니다.
~~~

- **재귀적 분할**(`RecursiveCharacterTextSplitter`): 단락 → 문장 → 공백(단어) 순으로 구분자를 차례로 적용해 의미 단위 보존 → 범용 표준 청킹 방식
  - ax `02.ipynb`도 이 분할기 사용: chunk_size 90, chunk_overlap 20, separator 줄은 주석 처리
- 의미론적 분할(Semantic Chunking)
  - 작동 원리: 문장 단위 분할 후 인접 문장 간 코사인 유사도를 연속 산출 → 임계값(Threshold) 이하로 급락하는 경계면(Breakpoint)에서 분리
  - 기술적 특성: 청크 내 의미론적 응집도를 높여 재현율(Recall)·정확도 향상, 인덱싱 단계에서 임베딩 추론이 많아 레이턴시·API 비용 부담
- 청크 크기와 오버랩의 트레이드오프
  - 크기가 작을 때: 검색은 정밀해지지만 문장의 앞뒤 인과관계 누락 가능
  - 크기가 클 때: 문맥은 유지되지만 무관한 문맥이 포함되어 노이즈 발생
  - **청크 오버랩**(Chunk Overlap): 앞 청크 끝부분을 뒤 청크 시작에 중복 포함 → 경계면 문맥 단절 방지

| 설정 항목 | 작은 값 설정 시 | 큰 값 설정 시 |
| --- | --- | --- |
| 청크 크기 (Size) | 검색 정밀도 향상, 문맥 누락 위험 | 문맥 풍부함, 연산량 및 노이즈 증가 |
| 청크 오버랩 (Overlap) | 중복 데이터 최소화, 경계 단절 위험 | 문맥 연속성 보장, 저장 공간 및 중복 증가 |

~~~python
# 문맥이 끊어지기 쉬운 연속된 문장을 정의합니다.
notice_text = "기숙사 입사 신청은 8월 1일부터 시작됩니다. 제출 서류는 건강진단서이며 보건소에서 발급 가능합니다."

# 청크 크기 25, 오버랩 10으로 설정하여 분할기를 구성합니다.

    chunk_size=25,
    chunk_overlap=10    # 앞 조각의 마지막 10글자를 다음 조각 앞부분에 복사합니다.
)

# 텍스트를 분할합니다.
overlap_chunks = overlap_splitter.split_text(notice_text)

# 오버랩 적용 결과를 확인합니다.
for idx, chunk in enumerate(overlap_chunks):
    print(f"오버랩 청크 {idx + 1}: {chunk}")
~~~

**4장 1강 : 키워드 검색 vs 벡터 검색 (1)**

키워드 유사성 조회

- **BM25** - 검색 알고리즘 ( Best Matching )

> 교재 · 4장 1강

- 글자 찾기 vs 의미 찾기: 키워드 검색은 글자가 똑같은지(단어 찾기 게임), 벡터 검색은 문장의 속뜻이 같은지(눈치 빠른 친구) 확인
- 키워드 검색(BM25): 입력 단어가 문서에 얼마나 자주 등장하는지 셈 → '컴퓨터'로 검색하면 'PC'라고 적힌 문서는 못 찾음
- 벡터 검색(Semantic Search): 문장을 벡터로 바꿔 의미가 가장 유사한 문서를 찾음 → "우울할 때 읽기 좋은 책"에 '우울'이 없어도 위로가 되는 책을 찾음
- 사용 프로그램에 `rank_bm25` 추가

~~~python
import os
from dotenv import load_dotenv
from rank_bm25 import BM25Okapi
from langchain_openai import OpenAIEmbeddings
from langchain.chat_models import init_chat_model
import numpy as np

load_dotenv()

# 우리가 검색할 대상이 되는 3개의 가상 문서 리스트입니다.
documents = [
    "애플의 새로운 스마트폰 아이폰 15가 출시되었습니다.",
    "삼성전자의 갤럭시 S24는 AI 기능이 뛰어납니다.",
    "현대자동차의 전기차 아이오닉은 연비가 훌륭합니다."
]

# ---------------------------------------------------------
# [1] 키워드 검색 (BM25) 준비
# ---------------------------------------------------------
# 문서를 띄어쓰기 기준으로 쪼개어 단어 리스트로 만듭니다.
tokenized_docs = [doc.split(" ") for doc in documents]
bm25 = BM25Okapi(tokenized_docs)

# ---------------------------------------------------------
# [2] 벡터 검색 준비 및 gpt-5-mini 모델 선언
# ---------------------------------------------------------
# 의미 검색을 위해 문장을 숫자로 바꾸는 임베딩 모델입니다.
embeddings_model = OpenAIEmbeddings(model="text-embedding-3-small")
doc_vectors = embeddings_model.embed_documents(documents)

model = init_chat_model(
    model_provider="openai",
    model="gpt-5-mini",
    temperature=0
)

# ---------------------------------------------------------
# [3] 검색 실행 및 비교
# ---------------------------------------------------------
# 검색어 (아이폰이라는 정확한 단어가 없습니다)
query = "사과 모양 로고가 있는 휴대폰"
print(f"질문: {query}\n")

# --- 키워드 검색 결과 ---
tokenized_query = query.split(" ")
bm25_scores = bm25.get_scores(tokenized_query)
best_bm25_index = np.argmax(bm25_scores)

print("[키워드 검색 1위 문서]")
print(documents[best_bm25_index])
# 엉뚱한 결과가 나옵니다. ('사과', '로고'라는 글자가 없기 때문)

# --- 벡터 검색 결과 ---
query_vector = embeddings_model.embed_query(query)
vector_scores = [np.dot(query_vector, doc_vec) for doc_vec in doc_vectors]
best_vector_index = np.argmax(vector_scores)

print("\n[벡터 검색 1위 문서]")
print(documents[best_vector_index]) 
# 정답을 찾습니다. ('사과 모양 휴대폰' = '아이폰' 이라는 의미를 파악)
~~~

> 교재 · 5장 1강

- BM25 = Best Matching 25: 단어 빈도(TF)와 역문서 빈도(IDF)를 종합 계산해 순위를 매기는 대표 키워드 검색 알고리즘
  - 단어 빈도(TF): 검색 단어가 한 문서 안에 자주 등장할수록 관련도 점수 상승
  - 역문서 빈도(IDF): 여러 문서에 흔한 일반 단어는 가중치 ↓, 희귀한 핵심 단어는 가중치 ↑
  - 문서 길이 정규화: 문서가 비정상적으로 길어 점수가 과도하게 높아지지 않도록 보정
- 의미 추론보다 고유명사·전문 용어가 본문에 실제로 있는지를 빠르고 정확하게 찾는 데 탁월

| 의미 탐색형 | 일상 구어체, 동의어, 상황 묘사 중심 | 벡터 검색 (Vector) |

2. **Reranking**
   - 많이 가져온 후보 → 정밀 모델로 재순위 → 최종 상위만 사용

> 교재 · 4장 3강

- Re-ranking(재정렬): 1차로 빠르게 건져낸 문서 후보군을 정밀하게 다시 채점해 상위권으로 재배치
- **2단계 검색**(2-Stage Search)
  - 1단계 Retrieval(빠른 추출): 수만 건 이상의 DB에서 관련 가능성 있는 상위 문서(Top-N, 보통 10~30개) 수집 — 키워드·벡터·하이브리드 검색 사용
  - 2단계 Re-ranking(정밀 재배열): 1단계 소수 문서만 대상으로 질문과 문서 문맥을 1:1 정밀 대조 → 최종 상위(Top-K, 보통 2~5개)를 최상단에 재배치
- Bi-Encoder (1차 검색 모델)
  - 질문과 문서를 각각 독립된 벡터로 변환한 뒤 각도(유사도)만 비교
  - 속도가 매우 빨라 수백만 문서를 훑을 수 있지만 문맥의 세밀한 상호작용을 놓칠 수 있음
- **Cross-Encoder** (재정렬 모델)
  - 질문과 문서를 하나의 쌍([질문 + 문서])으로 묶어 신경망에 동시에 통과
  - 질문 단어와 문서 단어의 관계를 깊이 분석 → 정확도가 매우 높음
  - 연산량이 많아 느리므로 1차 검색으로 추린 소수 문서에만 적용

~~~python
from sentence_transformers import CrossEncoder

# 1차 검색으로 건져온 가상의 문서 리스트 준비
documents = [
    "애플의 새로운 스마트폰 아이폰 15가 출시되었습니다.",
    "사과는 껍질이 붉고 단단하며 당도가 높은 것이 맛있습니다.",
    "삼성전자의 갤럭시 S24는 온디바이스 AI 기능이 뛰어납니다."
]

# 사용자의 실제 질문 정의
query = "맛있는 사과를 고르는 요령이 궁금해요"

# 질문과 문서를 1:1 쌍으로 결합
# Cross-Encoder는 질문과 문서를 한 번에 입력받아 분석합니다.
sentence_pairs = [[query, doc] for doc in documents]

# 연관성 평가 전용 경량 Cross-Encoder 모델 로드
reranker_model = CrossEncoder("Dongjin-kr/ko-reranker")

# 각 문서 쌍의 연관성 점수 계산 (점수가 높을수록 밀접함)
scores = reranker_model.predict(sentence_pairs)

# 점수를 기준으로 내림차순(높은 순) 정렬
ranked_results = sorted(
    zip(documents, scores),
    key=lambda x: x[1],
    reverse=True
)

# 재정렬 결과 확인
print(f"질문: {query}\n")
print("[Re-ranking 순위 결과]")
for idx, (doc, score) in enumerate(ranked_results):
    print(f"{idx + 1}위 (점수: {score:.4f}): {doc}")
~~~

**4장 4강 : Query 변환 기법 (1)**

1. **Query Rewrite** 기법
   - 애매한 질문 → LLM이 검색용으로 다듬음 → 검색 정확도 ↑

> 교재 · 4장 4강

- **Query 변환**(Query Transformation): 사용자의 자연어 질문을 검색 시스템이 이해하기 쉬운 최적의 표현으로 재작성하는 전처리 기법
- 검색 전단계(Pre-Retrieval) 최적화가 필요한 이유
  - 어휘 불일치 해소: 구어체 질문과 DB 문서 간 단어 표현 차이 극복
  - 모호성 제거: 오타, 축약어, 생략된 주어·대명사를 명확한 단어로 보완
  - 검색 품질 사전 확보: 잘못된 질의로 인한 1차 검색 실패를 선제 차단

| 기법 | 영문 표기 | 핵심 동작 | 최적 적용 시나리오 |
| --- | --- | --- | --- |
| 질문 재작성 | Query Rewrite | 맞춤법 교정 및 핵심 명사 중심 재구성 | 질문이 지나치게 짧거나 은어·오타가 포함된 경우 |
| 가설 문서 임베딩 | HyDE | 가상의 예상 답변 문서를 먼저 생성 후 검색 | 질문과 정답 문서 간의 문체·전문성 격차가 큰 경우 |
| 질문 라우팅 | Query Routing | 질문의 성격을 판별하여 저장소 경로 지정 | 복수의 특화 데이터베이스(문서, SQL, 웹)가 존재하는 경우 |
| 대화 맥락 반영 | Memory 기반 검색 | 직전 대화 기록을 참조해 생략된 대명사 복원 | 멀티턴 챗봇 환경에서 연속된 질문을 처리하는 경우 |

- Query Rewrite: 모호한 구어체 질문을 검색 엔진이 식별하기 쉬운 표준 단어로, LLM이 핵심 키워드 문장으로 재작성

~~~python
# 맥락 복원을 위한 프롬프트 정의
memory_prompt = PromptTemplate.from_template(
    "이전 대화 내용을 바탕으로 현재 질문에 생략된 맥락과 대명사를 복원하여 완전한 단일 검색 질문으로 재작성하세요.\n"
    "[이전 대화]\n"
    "{chat_history}\n"
    "[현재 질문]\n"
    "{question}\n"
    "복원된 질문:"
)

# 체인 연결
memory_chain = memory_prompt | model

# 연속 대화 상황 설정
history = "사용자: 어제 개봉한 마블 영화 이름이 뭐야?\nAI: '데드풀과 울버린'입니다."
follow_up_query = "그거 주인공 배우가 누구야?"

# 문맥 복원 질의 생성
contextualized_query = memory_chain.invoke({
    "chat_history": history,
    "question": follow_up_query
})

print(f"원래 질문: {follow_up_query}")
print(f"맥락 복원 질문: {contextualized_query.content}")
~~~

## 핵심 개념

- LLM 한계: 지식 컷오프(학습 시점 이후 모름) · 환각(모를 때 그럴듯한 거짓)
- RAG = 검색(외부 지식·임베딩) → 증강(프롬프트에 문맥 주입) → 생성(LLM 답변), 파인튜닝과 달리 모델 파라미터 그대로
- 파이프라인: 인덱싱(수집 → 분할 → 임베딩·저장, ETL) / 질의(검색 → 생성), 단계별 병목 추적
- 임베딩 = 텍스트 → 1,536차원 실수 벡터 · 유사도 = 코사인(-1~1) / 유클리디안(0에 가까울수록 유사) / 내적(방향+크기) · 대규모는 ANN
- 청킹: 입력 창 한계·의미 선명도·검색 효율 · 재귀적 분할이 표준 · chunk_size/overlap 트레이드오프는 품질 평가로 조정
- 검색 고도화: BM25(TF·IDF 키워드) vs 벡터 검색 · Re-ranking(Bi-Encoder → Cross-Encoder 2단계) · Query 변환(Rewrite·HyDE·Routing·Memory)

## 필기 ↔ 교재 비교

| 항목 | 필기 | 교재 | 결과 |
| --- | --- | --- | --- |
| 강의 구분 | 제목 없이 한 덩어리 | 1장 1~5강, 4장 1·3·4강 | 교재 강 순서로 나눔 |
| API 키 등록 | 시스템 환경 변수(`sysdm.cpl`) | 루트 .env + `load_dotenv()` | 필기 유지 + 교재 방식 병기 |
| RAG 3단계 | 검색·증강·생성 | 1-1 오픈북 비유, 1-2 5단계 | 필기 유지 + 교재 합침 |
| ETL | Extract·Transform·Load(빈칸) | 수집 → 분할 → 임베딩·저장 | Load를 1-2 「저장」으로 채움 |
| 유사도 3종 | 범위·방향 메모 | 1-4 정의·범위·활용 표 | 필기 유지 + 표 |
| 청킹 | 5줄 | 1-5 배경·전략·트레이드오프 | 필기 유지 + 교재 합침 |
| Rewrite·Reranking | 「증강 - 프롬프트」 아래 | 4-4 검색 전단계, 4-3 1차 검색 뒤 | 필기 문장 유지, 강별로 나눔 |
| 파인튜닝 | 파라미터 유지 + 작은 파라미터 학습 → LoRA | 파라미터(가중치) 재학습 | 필기 유지 + 「확인」 |

## 확인이 필요한 사항

⚠ 오탈 이중 기록
- 필기 OPEN_API_KEY → 본문 `OPENAI_API_KEY` (교재 .env·ax test 표기)
- 유클리언 → 유클리디안 (교재 「유클리디안 거리」) / Rewrite Query → Query Rewrite (교재 4장 4강)
- 증강 아래 번호 「1. Rewrite / 1. Reranking」 → 1.·2.로 교정, 강 순서상 Reranking(4-3)을 먼저 배치 / ETL 「Load :」 빈칸 → 교재 1-2 「벡터 DB에 저장」으로 채움

⚠ 파인튜닝 정의 — 필기 「기존 파라미터 유지 + 새로 추가된 작은 파라미터만 학습 → LoRA」는 교재 1-1 파인튜닝 정의(모델 파라미터 재학습)와 다르고, 「파라미터 그대로」는 교재에서 RAG 쪽 설명. LoRA·ETL 용어는 교재에 없음. 상세해설 HTML은 이 문장을 LoRA(파라미터 효율 파인튜닝) 방식 설명으로 봄 → 수업 설명 확인 필요

⚠ 용어·위치 — BM25 「Best Matching」은 교재 5장 1강 용어 사전 「Best Matching 25」. 필기는 Rewrite·Reranking을 「증강 - 프롬프트」 아래 두었으나 교재는 Query 변환을 검색 전단계(Pre-Retrieval), Re-ranking을 1차 검색 뒤 2단계로 설명. 「의미적 유의성 ↓」은 교재 1-5 「벡터의 의미 표현력 약화」와 같은 자리

⚠ ax ↔ 교재 코드 차이
- ax: 시스템 환경 변수를 `os.getenv`로 직접 읽음(load_dotenv 없음), 모델 `gpt-6-luna`
- ax 키 이름: test는 OPENAI_API_KEY, 02·similarity는 `OPENAI_API_KEY_TUTOR`
- 교재: .env + `load_dotenv()`, gpt-5-mini + temperature=0

⚠ 교재 원문 — 4장 1강 키워드 검색 주석은 「엉뚱한 결과가 나옵니다」인데 교재 출력은 키워드·벡터 모두 아이폰 문서. 4장 4강 HyDE 프롬프트 「한 달락」은 교재 원문(단락 오탈로 보임), 코드 그대로 둠
