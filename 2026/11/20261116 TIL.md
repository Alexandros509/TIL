## 어제의 복습

1. 컴퓨터가 자연어 문장의 의미를 이해하고 상호 간의 유사성을 계산할 수 있도록 다차원 숫자 배열로 변환하는 기술
   - 임베딩 (Embedding)
2. 두 텍스트의 글자 수나 문서 길이가 크게 다르더라도, 담고 있는 주제와 의미적 방향성이 일치하는지 판별하기 위해 자연어 검색에서 가장 표준적으로 쓰이는 유사도 측정 방식
   - 코사인 유사도 (Cosine Similarity)
3. 분할된 청크 사이의 경계에서 문장이나 단어가 끊어져 문맥이 단절되는 것을 방지하기 위해, 앞 청크의 끝부분 일부를 뒤 청크의 시작 부분에 중복 포함시키는 설정값
   - 청크 오버랩(chunk_overlap)
4. LangChain에서 본문 텍스트(page_content)와 부가 정보(metadata)를 하나의 묶음으로 다루는 기본 클래스
   - Document
5. 대규모 벡터 데이터베이스 환경에서, 전체 데이터를 일일이 비교하는 전수 조사 대신 벡터 공간을 사전 군집화하여 오차 범위를 허용하면서 검색 속도를 획기적으로 향상시키는 색인 기술
   - ANN(근사 최근접 이웃)

**2장 4강 : 임베딩 생성 (1)**

`embed_documents`로 청크를 벡터로 바꾸는 기본 실습은 [어제 TIL 2장 4강](./20261113%20TIL.md)을 본다. 오늘은 같은 청크를 한 번 더 임베딩할 때 API를 다시 부르지 않도록 캐시를 붙인다.

> 교재 · 2장 4강

- 임베딩 모델과 로컬 저장소를 결합한 **캐시 임베딩** 객체로, 첫 실행은 API를 호출하고 두 번째부터는 캐시를 재사용한다
- ax `02_04_2.ipynb`는 `CacheBackedEmbeddings`와 로컬 파일 저장소를 사용한다
- 저장 경로는 ./cache/, namespace는 library_rules

```python
import time
from langchain_classic.embeddings import CacheBackedEmbeddings
from langchain_classic.storage import LocalFileStore
from langchain_openai import OpenAIEmbeddings

embedding_model = OpenAIEmbeddings(model="text-embedding-3-small")

library_rule_chunks = [
    "[2026학년도 중앙도서관 대출 및 열람 규정]\n제1조(대출 자격) 본교 재학생 및 휴학생은 학생증을 제시한 후 도서를 대출할 수 있습니다.",
    "제2조(대출 권수 및 기간) 학부생은 1인당 최대 5권까지 대출할 수 있으며 대출 기간은 14일입니다.\n단, 학술 연구용 특수 도서는 7일간 대출 가능하며 연장은 불가능합니다.",
    "제3조(연체 및 제재) 반납 기한을 초과할 경우 연체 일수만큼 대출이 정지됩니다."
]

store = LocalFileStore("./cache/")

cached_embedder = CacheBackedEmbeddings.from_bytes_store(
    underlying_embeddings=embedding_model,
    document_embedding_cache=store,
    namespace="library_rules"
)
```

```text
UserWarning: Using default key encoder: SHA-1 is *not* collision-resistant.
While acceptable for most cache scenarios, a motivated attacker can craft two different payloads that map to the same cache key.
If that risk matters in your environment, supply a stronger encoder (e.g. SHA-256 or BLAKE2) via the `key_encoder` argument.
If you change the key encoder, consider also creating a new cache, to avoid (the potential for) collisions with existing keys.
```

```python
# 최초 실행 - 임베딩 생성 -> 캐시 기록
start_time = time.time()
vectors_first = cached_embedder.embed_documents(library_rule_chunks)
end_time = time.time() - start_time # 소요 시간
print(f"1번째 실행 소요시간: {end_time:.4f}초")

start_time = time.time()
vectors_second = cached_embedder.embed_documents(library_rule_chunks)
end_time = time.time() - start_time # 소요 시간
print(f"2번째 실행 소요시간: {end_time:.4f}초")

print(f"동일한 벡터값: {vectors_first == vectors_second}")
```

```text

2번째 실행 소요시간: 0.0430초
동일한 벡터값: True
```

- 2번째는 1번째보다 짧고, 벡터 값은 같다

> 교재 · 2장 5강

- 어제까지는 메모리·파일 캐시 수준이었다. 이번 강은 PostgreSQL에 pgvector 확장을 얹어, 대용량 벡터를 보관하는 **벡터 데이터베이스**를 쓴다
- 일반 테이블 데이터와 임베딩 벡터를 하나의 데이터베이스에서 다룰 수 있다

- 청크별 고유 id를 붙여 저장(Upsert)한다
- 교안은 pgvector가 포함된 PostgreSQL 17 컨테이너를 띄워 사용한다. 연결 문자열은 환경 변수 `DATABASE_URL`로 읽는다

ax `02_05.ipynb`:

```python
import os
from dotenv import load_dotenv
from langchain_openai import OpenAIEmbeddings
from langchain_postgres.vectorstores import PGVector


load_dotenv()

embedding_model = OpenAIEmbeddings(
    model="text-embedding-3-small"
)

connection_url = os.getenv("DATABASE_URL")

vector_store = PGVector(
  embeddings=embedding_model,
  connection=connection_url,
  collection_name="library_rules",
  use_jsonb=True # 메타데이터를 JSONB로 저장
)
```

```python

    "제3조(연체 및 제재) 반납 기한을 초과할 경우 연체 일수만큼 대출이 정지됩니다."

**2장 7강 : 인덱싱 파이프라인 통합·증분 갱신 (1)**

> 교재 · 2장 7강

- 규정이 바뀌면 벡터 저장소를 처음부터 다시 채우지 않고, 바뀐 출처만 **증분 갱신**한다
- `SQLRecordManager`가 소스 id를 추적하고, index의 cleanup으로 정리 방식을 고른다
- ax 주석의 세 옵션
  - none: 증분 관리 X
  - incremental: 중복된 레코드가 있으면 삭제하고 새로 추가
  - full: 전체를 삭제하고 다시 추가

```

**3장 1강 : Retriever 구성과 질의 임베딩 (1)**

`as_retriever()` : VectorStore를 Retriever로 바꿔주는 메서드

> 교재 · 3장 1강

- 저장소에 질문을 그대로 넣을 수 없다. 질문도 문서와 같은 임베딩 모델로 벡터로 바꾼 뒤, Retriever가 가까운 문서를 가져온다
- `as_retriever()`가 그 검색기를 만들어 주는 메서드다. 체인에 연결하는 상세 코드는 이후 강의

**3장 3강 : Top-k 설정과 score threshold (1)**

| 메서드                                                 | 점수 방향           | threshold 의미              |
| ------------------------------------------------------ | ------------------- | --------------------------- |
| similarity_search_with_score (거리)                    | 낮을수록 유사       | 직접 threshold 잘 안 씀     |
| similarity_search_with_relevance_scores                | 높을수록 유사 (0~1) | 높을수록 엄격               |
| as_retriever(search_type="similarity_score_threshold") | 높을수록 유사       | score_threshold 이상만 통과 |

`similarity_search_with_score`: 1-코사인 유사도 = 코사인 거리

- 0~0.35 : 적합
- 0.35~0.7 : 보통
- 0.7~ : X

> 교재 · 3장 3강

- Top-k는 상위 몇 개를 가져올지, threshold는 얼마나 가까운 것만 통과시킬지다
- 2장 5강 k=1·k=3 실습이 이 설정의 앞부분이다

**5장 3강 : RRF·가중치 튜닝 (1)**

**RRF (Reciprocal Rank Fusion)**

- 여러 검색 결과의 순위를 합치는 방법
- 임베딩 + 코사인 거리 + BM25

하는 일

서로 다른 검색 방식(예: 임베딩 검색 + BM25/TF-IDF 검색)의 결과를 하나로 합칠 때 씁니다

공식

$$
\text{RRF}(d) = \sum_{i} \frac{1}{k + \text{rank}_i(d)}
$$

- `rank_i(d)` : 검색 방식 \(i\)에서 문서 \(d\)의 순위
- `k` : 상수 (보통 60)
- 여러 검색에서 상위에 자주 나온 문서일수록 높은 점수를 받음

특징

| 항목 | 내용                                                |
| ---- | --------------------------------------------------- |
| 장점 | 점수 스케일이 달라도 순위만 보고 합칠 수 있음       |
| 장점 | 구현이 단순하고 효과적                              |
| 단점 | 점수 자체의 차이는 무시함 (순위만 봄)               |
| 쓰임 | 하이브리드 검색 (Dense + Sparse)에서 가장 많이 사용 |

> 교재 · 5장 3강

- 점수 단위가 다른 검색기를 더할 때, 순위만 보고 합치는 방법이다
- 필기의 「임베딩 + 코사인 거리 + BM25」는 확인란

**6장 1강 : 평가셋 구성과 검색 지표 (1)**

검색 지표 (Retrieval Metrics)

검색 단계에서 “관련 있는 문서를 얼마나 잘 찾았는가”를 평가합니다.

| 지표               | 의미                                              |
| ------------------ | ------------------------------------------------- |
| Precision (정밀도) | 검색된 문서 중 실제로 관련 있는 비율              |
| Recall (재현율)    | 관련 있는 문서 중 검색에 걸린 비율                |
| F1                 | Precision과 Recall의 조화평균 (둘의 균형)         |
| MRR / nDCG         | 순위 품질 (상위권에 관련 문서가 얼마나 잘 있는지) |

공식

Precision

$$
\text{Precision} = \frac{TP}{TP + FP}
$$

Recall

$$
\text{Recall} = \frac{TP}{TP + FN}
$$

F1

$$
\text{F1} = \frac{2 \times \text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}
$$

용어 풀이

- TP (True Positive): 관련 있는 문서를 맞게 검색한 경우
- FP (False Positive): 관련 없는 문서를 잘못 검색한 경우
- FN (False Negative): 관련 있는 문서를 검색하지 못한 경우

평가셋 Golden Set

> 교재 · 6장 1강

- 평가셋(골든셋)은 질문·정답·근거 문서를 미리 정해 둔 채점용 데이터다
- 위 지표로 「문서를 잘 찾았는지」를 본다. 구축·RAGAS 측정은 7장

**6장 2강 : 생성 지표와 실패 원인 분석 (1)**

생성 지표 (Generation Metrics)

LLM이 만든 최종 답변의 품질을 평가합니다.

| 지표                       | 의미                                                   |
| -------------------------- | ------------------------------------------------------ |
| Faithfulness               | 답변이 검색된 문서에 충실한가 (환각 여부)              |
| Answer Relevance           | 질문에 얼마나 잘 답했는가 (질문 - 답변, 임베딩 유사도) |
| Context Precision / Recall | 검색된 문맥이 답변에 얼마나 유용했는가                 |
| Correctness                | 사실적으로 맞는가                                      |

차이 요약

- 검색 지표: 문서를 잘 찾았는지 (Precision, Recall 등)
- 생성 지표: 그 문서로 만든 답변이 좋은지 (Faithfulness, Relevance 등)

> 교재 · 6장 2강

- 검색이 잘돼도 답변이 문서를 벗어나면 생성 지표가 떨어진다
- 실패 유형을 나누고 파이프라인을 고치는 실습은 이후 7장

## 확인이 필요한 사항

⚠ 오탈 이중 기록

- 필기 Inversion Document Frequency → 본문 Inverse Document Frequency (IDF)
- 점수 표 앞 빈 열(`||메서드|...`)을 제거하고, 표 밖으로 떨어진 「1-코사인 유사도 = 코사인 거리」행은 표 아래 문장으로 둠
- 생성 지표 Answer Relevance 칸의 원문 「질문 - 답변 | 임베딩 유사도」는 표 안 세로줄이라 깨져, 본문에서는 쉼표로 바꿈

⚠ 필기 거리 구간(0~0.35 적합) vs 튜터 `02_05` 정답 청크 점수 0.4440. 필기 기준으로는 ‘보통’ 구간에 해당. 수업에서 쓴 스케일인지 확인 필요

⚠ RRF 설명 「임베딩 + 코사인 거리 + BM25」: 같은 필기 ‘하는 일’은 임베딩 검색 + BM25/TF-IDF. 코사인 거리를 세 번째 검색기처럼 나열한 부분 확인

⚠ ax(튜터 GitHub) ↔ PC

- 코드는 튜터 원본. `02_04_2` 소요시간 튜터 0.5841→0.0430초, PC 1.0809→0.0162초 (소스 공백만 다름)
