## 오늘 공부한 내용

### 어제의 복습
`git init` 로컬 저장소 생성

```text
 - working directory ------------> staging area / index -----------> repository  
                    git add                             git commit  
                                                        <-----------  
                                                        git reset --soft (커밋 취소)  
                    <-----------------------------------------------  
                                                        git reset --mixed (디폴트)  
 <------------------------------------------------------------------
                                                        git reset --hard
```

- `git reflog`
- `git log`
- `git add` > `git status` (확인) > `git add -p` (선택) > `git diff --staged` (커밋 전 확인)

**add와 함께 커밋**
- `git commit -a -m ____`
- `git commit -am ____`

**마지막 커밋 수정**
- `git commit --amend -m "메세지 컨벤션"`

**reset vs revert**
- `reset` : 복구 시점까지만 기록이 남는다 (기록 유지 X)
- `revert` : 복구 시점의 새로운 커밋을 생성 (기록은 유지)

### 브랜치 및 병합/재배치

```text
브랜치
 main / master - 완성본  
  생성 git branch branchname   feature/   
  이동 git checkout/switch branchname  
  생성+이동 git checkout -b bname  
                     switch -c bname  
  삭제 git branch -d bname  
                     -D (d, D 다른 브랜치에서 삭제)   
  변경 git branch -m bn  
                    -M bn (m, M 변경하고자 하는 브랜치로 이동 > 변경)  

  병합 git merge bn
      1) Fast-Forward
         main 변경 사항 X. 서브 브랜치 라인 복사
      2) 3-way
         main sub 병합 > 새로운 커밋

  재배치 git rebase bn
        커밋 기록 재배치. 깔끔하게 커밋 이력을 선형으로 정리하기 위해
            충돌 > 해결 (git add) > 진행 (git rebase --continue)
                   스킵 ( git rebase --skip) 현재 해결 건너뛰기 
                   중단 ( git rebase --abort) 전체 중단
```

### 원격 저장소 및 Github
- **push**: `git push origin bn(원격브랜치) -u`
- **remote**: `git remote add 원격저장소별칭 원격저장소주소` (변경 시 `set-url`)
- **pull**: `git pull origin bn` (`pull` = `fetch` + `merge`)
- **fetch**: 원격 저장소에서 가져옴.
- 실무에서는 `git pull --rebase`를 많이 씀.

### GitHub 협업 및 PR 관리
- 코드 히스토리가 꼬여있으면 Github에서 `able to merge`가 안 뜸.  
- PR(Pull Request)은 관련자 검토 승인 요청 느낌.  


**PR 작성 예시**

```text
#작업 내용
...

#특이사항
...

#테스트 방법
...

[x] 항목1
[ ] 항목2
```

### GitHub PR 및 브랜치 관리
- PR 병합 완료 후: `confirm merge` > `delete branch` (필요 없어진 브랜치 삭제)

**Branch Protection Rules (main 브랜치 보호 설정)**
- **경로**: `Settings` > `Rules` > `Rulesets` > `New ruleset` > `New branch ruleset`
- **적용 대상**: `Target branches` > `Add target` > `Include by pattern` (문자열 `main` 입력) > `Add inclusion pattern` (확인)
- **주요 설정**:
  - `Require a pull request before merging` 체크
  - 선택 옵션: `Required approvals` (설정하지 않으면 누구든지 올리고 얼마든지 수정 가능. 특정 팀이나 코드 주인의 리뷰 요청 및 소통 해결을 필수로 지정할 수 있음)
  - `Allow merge methods` 중 `squash` 활성화 (커밋 여러 개를 하나로 합쳐서 이력을 깔끔하게 유지하는 병합 전략)
  - `Active` 상태로 변경하여 적용

### 원격 저장소 동기화 및 템플릿 설정
- **Push 에러**: 원격 저장소에 로컬에 없는 작업(커밋)이 있을 때 발생.
  - 해결 명령어: `git pull --rebase origin main`
- **PR 템플릿 생성**:
  - 정해진 경로에 새 폴더 및 파일 생성: `.github/pull_request_template.md`
  - 적용: `git add .` > `git commit -m "docs: 풀리퀘스트 양식 추가"` > `git push origin main`
- **Issue 템플릿**: AI에게 많이 사용하는 초안 추천 예시를 요청하여 작성.

### GitHub Projects 및 작업 흐름 (Kanban)
- **Projects 탭**:
  - `New project` 생성 시 템플릿을 `Kanban`으로 설정하여 작업 흐름 파악.
  - 드래그 또는 `...`의 `move to column`으로 항목 이동 가능.
  - `Item`의 `label`로 상태 표시.
  - `Milestone`으로 데드라인, 유의할 점, 목표 등 설정.
  - `Create new issue`로 작업 단위 생성 (예: `gitex#2`).
- **PR 작업 흐름**:
  1. `git switch -c feature/order-process`
  2. 문서 작성 및 수정
  3. `git add`, `commit`, `push`
  4. GitHub `Pull requests` 탭 > `Create pull request` > 브랜치 선택 및 작성
  5. PR 본문에 `closes #2` 입력 시 병합될 때 해당 이슈가 자동으로 닫힘.

### Git 주요 명령어 모음
- `git fetch` : 원격 저장소에서 정보만 가져옴. (`pull` = `fetch` + `merge`)
- `git pull --rebase` : 실무에서 자주 사용하는 병합 방식.
- `git stash` : 작업 임시 저장.
- `git reflog` : 복구 시 사용.
- `git cherry-pick` : 특정 커밋 추출 및 접합. (너무 많이 사용하면 이력이 어지러워짐)
- `git tag` : 네이밍 및 버전 표기.
- `git ignore` : push 제외 항목 설정.
- `git rm --cached` : 스테이징 취소 명령어. (`reset` 외에도 사용 가능)
- `git restore` : 워킹 트리 취소 명령어.
- `git diff HEAD`, `<SHA1> <SHA2>` : 비교 명령어. (`--staged` 옵션만 알아도 충분히 활용 가능)

```markdown
## 질문 및 깨달음

### 퀴즈 오답 노트 및 해설

**2번 문항**
- **질문:** 작업이 미완성 상태일 때 변경 사항을 임시로 스택에 저장하고 워킹 트리를 마지막 커밋 상태로 되돌리는 Git 명령어는 무엇인가?
- **나의 답:** rebort (오답)
- **해설 및 깨달음:** 정답은 `git stash`. 현재 작업 디렉토리와 스테이징 영역의 변경사항을 스택에 임시 저장하고 복원(`pop`이나 `apply`)할 수 있어, 긴급하게 다른 브랜치로 전환해야 할 때 유용하다.

**3번 문항**
- **질문:** 코드 리뷰에서 리뷰어가 'Request changes'를 선택했을 때 발생하는 상황으로 옳은 것은?
- **나의 답:** C. 단순 참고용 의견이므로 머지에는 아무 영향이 없다 (오답)
- **해설 및 깨달음:** 'Request changes'는 버그, 보안 이슈 등 머지 전 반드시 수정이 필요한 경우 사용하는 액션이다. Branch Protection Rules가 설정되어 있다면 Approve하기 전까지 머지가 차단된다.

**4번 문항**
- **질문:** PR 본문에 'Closes #12'와 같이 특정 키워드와 Issue 번호를 함께 작성하면, PR이 머지될 때 자동으로 일어나는 동작은 무엇인가?
- **나의 답:** 병합 (오답)
- **해설 및 깨달음:** PR이 머지되는 순간 해당 Issue가 **자동으로 닫힌다**. 이를 통해 히스토리에서 어떤 작업이 문제를 해결했는지 추적할 수 있다.

**5번 문항**
- **질문:** GitHub Flow와 Git Flow를 비교한 설명 중 옳은 것은?
- **나의 답:** C. GitHub Flow는 브랜치 구조가 단순해 소규모·빠른 배포 주기의 팀에 적합하다 (정답)
- **해설 및 깨달음:** GitHub Flow는 main과 기능 브랜치만으로 동작하는 단순한 구조를 가진다. 반면 Git Flow는 복잡한 브랜치 구조를 가져 중대형 팀에 적합하다.
```

## 핵심 개념

- **GitHub Flow**: main과 기능 브랜치만으로 동작하는 단순한 협업 워크플로우.
- **Branch Protection Rules**: main 브랜치에 직접 푸시하는 것을 막고 PR과 리뷰를 강제하는 보호 설정.
- **Git Stash**: 미완성 작업을 임시로 스택에 저장하고 워킹 트리를 깨끗하게 비우는 기능.
- **Cherry-pick**: 다른 브랜치의 특정 커밋만 가져와 현재 브랜치에 적용하는 기능.

## 교재 보충

※ 아래 내용은 사용자의 필기를 보완하기 위해 교재에서 가져온 내용이다.

*   **git init vs git clone**
    *   `git init`은 새 프로젝트를 시작할 때 로컬에 `.git`을 생성한다.
    *   `git clone`은 이미 있는 원격 저장소의 전체 커밋 이력과 브랜치 정보를 복사해 온다.

*   **git rm --cached 주의사항**
    *   스테이징 영역(인덱스)에서만 파일을 제거하며, 로컬 파일 시스템에는 그대로 남는다.
    *   이미 원격(GitHub)에 push된 민감 정보(API Key 등)는 이 명령어나 `.gitignore`만으로 안전해지지 않으므로 즉시 폐기/재발급해야 한다.

*   **Fast-forward 방지 (`--no-ff`)**
    *   Fast-forward 조건이 충족되더라도 강제로 병합 커밋을 생성한다. 팀 프로젝트에서 브랜치의 분기 흔적을 히스토리에 명확히 남기기 위해 사용한다.

*   **Rebase 황금률**
    *   "공유된 커밋은 rebase하지 않는다." rebase는 커밋 해시를 변경하므로, 이미 원격 저장소에 push된 커밋을 rebase하면 다른 팀원과 심각한 충돌이 발생한다.

*   **충돌 마커 해석**
    *   `<<<<<<< HEAD`부터 `=======`까지는 현재 체크아웃된 브랜치의 내용, `=======`부터 `>>>>>>> 브랜치명`까지는 병합하려는 브랜치의 내용이다. 마커를 모두 제거하고 최종 코드만 남겨야 한다.

*   **PR 본문 구성 3요소**
    *   변경 이유(Why), 변경 내용(What), 테스트 방법(How to test)

## 문제 상황 / 시행착오

### 프로젝트 중 브랜치 충돌 발생
- GitHub의 main과 branch 최신화 과정에서 push & pull 진행 중 잦은 충돌이 생김.
- `dev/map` 브랜치에 내 로컬 컴퓨터에는 없는 새로운 커밋이 미리 존재하여 에러 발생.

## 해결 과정

### 브랜치 충돌 해결
- `git fetch` 후 `git switch`로 상태를 먼저 확인함.
- `git pull origin dev/map` 명령으로 원격의 최신 상태를 로컬로 가져와 합친 후, `git push origin dev/map`을 수행하여 정상적으로 업로드함.

작업이 미완성 상태일 때 변경 사항을 임시로 스택에 저장하고 워킹 트리를 마지막 커밋 상태로 되돌리는 Git 명령어는 무엇인가?

rebort


오답이에요
git stash는 현재 작업 디렉토리와 스테이징 영역의 변경사항을 스택에 임시 저장하고 워킹 트리를 마지막 커밋 상태로 되돌립니다. 이후 git stash pop이나 apply로 복원할 수 있어, 긴급하게 다른 브랜치로 전환해야 할 때 유용합니다.


3번 문항
코드 리뷰에서 리뷰어가 'Request changes'를 선택했을 때 발생하는 상황으로 옳은 것은?

C. 단순 참고용 의견이므로 머지에는 아무 영향이 없다


오답이에요
Request changes는 버그, 보안 이슈, 설계 문제처럼 머지 전 반드시 수정이 필요한 경우 사용하는 액션입니다. Branch Protection Rules가 설정되어 있다면 리뷰어가 재확인 후 Approve하기 전까지 머지가 차단되어, 문제 있는 코드가 실수로 배포되는 것을 막아줍니다.

4번 문항

병합


오답이에요
PR 본문에 Closes, Fixes, Resolves 등의 키워드와 Issue 번호를 함께 작성하면 PR이 머지되는 순간 해당 Issue가 자동으로 닫힙니다. 이를 통해 어떤 작업이 어떤 문제를 해결했는지 히스토리에서 추적할 수 있습니다.

5번 문항
GitHub Flow와 Git Flow를 비교한 설명 중 옳은 것은?

C. GitHub Flow는 브랜치 구조가 단순해 소규모·빠른 배포 주기의 팀에 적합하다

정답이에요
GitHub Flow는 main과 기능 브랜치만으로 동작하는 단순한 구조로, 소규모 팀이나 빠른 배포 주기에 적합합니다. 반면 Git Flow는 main, develop, feature, release, hotfix 등 복잡한 브랜치 구조를 가지며 중대형 팀의 버전 관리에 적합하고, 대형 팀의 짧은 주기 CI/CD 통합에는 Trunk-based Development가 더 적합합니다.
