## 오늘 공부한 내용

### 1. `git add` 전 확인 단계
커밋 전 코드를 점검하기 위해 다음 순서로 작업한다.
`git status` > `git add -p` > `git diff --staged`

- **`git add -p` (올리면서 검사하기)**
  전체 파일 내용을 한 번에 올리지 않고, 코드를 조각조각 확인하며 스테이징(add) 여부(y/n)를 디테일하게 결정한다.
- **`git diff --staged` (최종 커밋 전 더블 체크)**
  마지막으로 최종 점검을 수행한다.

### 2. 커밋 메시지 컨벤션
팀원들 간 지키기로 약속한 일종의 커밋 작성 규칙과 양식이다.

| 말머리 | 의미 |
|------|------|
| `feat:` | 기능 추가 |
| `fix:` | 버그 수정 |
| `docs:` | 문서화 |
| `refactor:` | 리팩토링 |
| `chore:` | 설정 변경 |
| `test:` | 테스트 코드 |

> **실제 적용 예시**
> ```bash
> git commit -m "feat: 로그인 기능 추가"
> git commit -m "docs: README 업데이트"
> ```

### 3. 스테이징 및 커밋 수정/변경

#### 1) `git reset` (되돌리기)
`git reset HEAD~`: 방금 한 최신 커밋 1개를 취소하는 명령어.

| 옵션 | 취소 범위 | 결과 |
|------|------|------|
| `--soft` | 커밋만 취소 | Staging 영역에 파일 남음 |
| `--mixed` | 커밋 + add 취소 | Working 디렉터리에 파일 남음 (디폴트) |
| `--hard` | 커밋 + add 취소 | 파일 변경 내역까지 전부 삭제 (복구 불가) |

#### 2) `git reflog` (블랙박스)
- 작업 및 수정한 모든 발자취를 기록해 둔 Reference log.
- `git reset --hard`로 삭제된 코드와 `git log`뿐만 아니라, `git reflog`에는 reset을 했다는 행위 자체도 기록된다.
- `HEAD@{0}`: 가장 최근에 한 행동을 의미한다.

#### 3) `git revert`
- 과거의 특정 커밋 내용을 취소하는 정반대의 새로운 커밋을 생성한다.
- 기존 커밋 역사(History)를 지우지 않고 커밋 기록을 유지하며 안전하게 변경 사항만 되돌린다.

### 4. 브랜치 (평행세계 / 시간선 분리)
독립적으로 개발할 때 사용하며, 작은 범위로 나누어 작업하는 것이 관례이다.

#### 브랜치 관리 명령어
- **생성**: `git branch 브랜치명` (물리적으로 분리되는 공간을 커밋 기반으로 추가. 단, 빈 폴더에서는 생성되지 않음)
- **확인**: `git branch` (* 표시가 현재 브랜치)
- **이동**: `git checkout 브랜치명` 또는 `git switch 브랜치명`
- **생성 및 이동**: `git switch -c 브랜치명`
- **삭제**: `git branch -d 브랜치명`
- **이름 변경**: `git branch -m 변경할브랜치명` (강제 변경 시 `-M` 옵션 사용)

#### 브랜치명 컨벤션
| 접두사 | 의미 | 예시 |
|------|------|------|
| `feature/` | 새 기능 개발 | `feature/order-form` |
| `fix/` | 오류 수정 | |
| `bugfix/` | 오류 수정 | |
| `hotfix/` | 긴급 수정 | |
| `chore/` | 로직과 무관한 설정/환경 변경 | |
| `release/` | 최종 테스트, 버전 관리 | |
| `test/` | 검증용 테스트 | |
| `docs/` | 문서 파일 추가 및 수정 | |
| `dev/` | feature 브랜치를 하나로 통합/테스트 | |

#### 브랜치 병합 (Merge)
- **Merge commit (3-way)**: 두 브랜치 모두 새로운 작업이 있을 때, 양쪽 역사를 합친 새로운 융합 커밋을 생성하여 병합. (`git merge 병합브랜치명`)
- **Fast-forward (빨리 감기)**: 기준 브랜치에 변경 사항이 없을 때, 별도 커밋 없이 기준 브랜치의 위치만 최신 작업 위치로 빨리 감아 이동.
- **Conflict**: 병합 중 발생하는 충돌 현상.

### 5. `git rebase`
- 브랜치가 파생되었던 기준점(Base)을 최신 위치로 다시 설정(Re-base).
- 복잡하게 얽힌 커밋 히스토리를 일직선으로 깔끔하게 정리한다.
- 충돌 발생 시:
  - 해결 후 진행: `git rebase --continue`
  - 현재 충돌 건너뛰기: `git rebase --skip`
  - 전체 중단: `git rebase --abort`

### 6. 기타 명령어 및 팁
- **`git stash`**: 브랜치 이동 시 임시 보관 (`git stash list`로 목록 확인, `git stash pop`으로 복구).
- **`git help 명령어`**: 명령어 도우미.

#### 원격 저장소 (GitHub)
- 작업 흐름: `PC 로컬 저장소 > push > 원격 저장소 > pull > 로컬 저장소`
- **설정 및 확인**:
  - `git remote add origin ssh주소`
  - `git remote -v` (저장된 원격 저장소 목록 확인)
- **다운로드**: `git clone ssh주소`
- **동기화**:
  - `git push origin main` (로컬 커밋 업로드)
  - `git pull origin main` (원격 데이터 다운로드)
  - 기본 고정 옵션: `-u` (`git push -u 원격브랜치별칭 원격브랜치주소`)

## 교재 보충

※ 아래 내용은 사용자의 필기를 보완하기 위해 교재에서 가져온 내용이다.

### [교재 보충] `git diff` 활용
📘 교재 보충: `git diff --stat`은 파일별 변경 규모(추가/삭제 줄 수)만 요약해서 확인하는 명령어이다.

### [교재 보충] `git restore` (워킹/스테이징 복원)
📘 교재 보충: `git restore <file>`은 커밋 이력을 변경하지 않고 워킹 디렉터리의 변경을 마지막 커밋 상태로 복원한다.
📘 교재 보충: `git restore --staged <file>`은 스테이징 영역에서 변경을 취소(add 취소)하는 역할을 한다.

### [교재 보충] HEAD 포인터
📘 교재 보충: HEAD는 현재 작업 중인 브랜치 또는 커밋을 가리키는 특수 포인터로, 브랜치를 전환하면 HEAD가 해당 브랜치로 이동하고 워킹 디렉터리도 그 상태로 자동 전환된다.

### [교재 보충] 병합(Merge) 주요 옵션
📘 교재 보충: `--no-ff` 옵션을 사용하면 Fast-forward 조건이 충족되더라도 반드시 병합 커밋을 강제 생성하여 히스토리에 브랜치 흔적을 남긴다.
📘 교재 보충: `--squash` 옵션은 브랜치의 여러 커밋을 하나로 압축하여 병합 대상 스테이징 영역에 올린다.

### [교재 보충] Rebase의 황금률
📘 교재 보충: "공유된 커밋은 rebase하지 않는다"는 규칙이다. 이미 원격 저장소에 push된 커밋을 rebase하면 다른 팀원의 히스토리와 심각한 충돌이 발생한다.

### [교재 보충] 충돌(Conflict) 해결 방법
📘 교재 보충: 충돌 발생 시 Git은 파일에 `<<<<<<< HEAD`, `=======`, `>>>>>>> 브랜치명` 형태의 마커를 삽입한다.
📘 교재 보충: 에디터에서 충돌 마커를 지우고 원하는 내용을 직접 남긴 후, `git add`와 `git commit`을 차례로 실행해 해결한다.

### [교재 보충] Fetch와 Pull --rebase
📘 교재 보충: `git fetch`는 원격 변경 사항을 가져오되 자동으로 merge하지 않아 안전하게 확인할 수 있다.
📘 교재 보충: `git pull --rebase`는 로컬 커밋을 원격의 새 커밋 위에 선형으로 재배치하여 히스토리를 깔끔하게 유지할 때 사용한다.

## 문제 상황 / 시행착오

- `reflog` 테스트 중 `--hard` 옵션으로 삭제된 커밋은 다시 `--hard`로 복구해야 함을 확인했다.
- `reset` 이후의 상태 메시지 확인:
  `Unstaged changes after reset:`
  `M       MEMBER.md`
  `D       PRODUCT.md`
  해당 메시지를 통해 파일의 수정(M)과 삭제(D) 상태를 직접 확인했다.

## 느낀 점

- **"Merge하면 양쪽 다 변하나요?"**
  깨달음: 병합은 단방향 흡수다. `git merge b`를 치면 내가 있는 a 브랜치만 진화하고, b 브랜치는 과거 상태 그대로 멈춰있다.
- **"빈 폴더에서는 branch가 왜 안 만들어지나요?"**
  깨달음: 브랜치는 '커밋(발자국)'을 가리키는 이정표인데, 빈 폴더는 최초의 커밋(Initial Commit)조차 없어서 이정표가 가리킬 대상이 없기 때문.
- **"브랜치 이름 바꿀 때(-M) add, commit을 해야 하나요?"**
  깨달음: 브랜치 이름 변경은 파일 내용(코드)이 바뀐 게 아니라 캡슐의 '이름표'만 바꿔 낀 것이므로, commit을 할 필요 없이 바로 push 등 다음 작업을 하면 된다.
- **"Push 된 커밋은 왜 Rebase 하면 안 되나요?"**
  깨달음: Rebase는 커밋 식별자를 바꾸는 '역사 조작'이므로, 이미 깃허브에 공유되어 남들이 다운로드해 간 과거를 나 혼자 조작하면 팀원들의 Git 세계선이 전부 붕괴(충돌)하기 때문.

"Merge하면 양쪽 다 변하나요?"

깨달음: 병합은 단방향 흡수다. git merge b를 치면 내가 있는 a 브랜치만 진화하고, b 브랜치는 과거 상태 그대로 멈춰있다.

"빈 폴더에서는 branch가 왜 안 만들어지나요?"

깨달음: 브랜치는 '커밋(발자국)'을 가리키는 이정표인데, 빈 폴더는 최초의 커밋(Initial Commit)조차 없어서 이정표가 가리킬 대상이 없기 때문.

"브랜치 이름 바꿀 때(-M) add, commit을 해야 하나요?"

깨달음: 브랜치 이름 변경은 파일 내용(코드)이 바뀐 게 아니라 캡슐의 '이름표'만 바꿔 낀 것이므로, commit을 할 필요 없이 바로 push 등 다음 작업을 하면 된다.

"Push 된 커밋은 왜 Rebase 하면 안 되나요?"

깨달음: Rebase는 커밋 식별자를 바꾸는 '역사 조작'이므로, 이미 깃허브에 공유되어 남들이 다운로드해 간 과거를 나 혼자 조작하면 팀원들의 Git 세계선이 전부 붕괴(충돌)하기 때문.
